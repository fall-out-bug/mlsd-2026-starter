# HW2: проект подготовки клиентских признаков

Соберите работающий проект на Docker Compose: Airflow управляет обработкой,
Spark рассчитывает признаки Online Retail II, SeaweedFS хранит CSV/Parquet
через S3 API, Redis хранит клиентские признаки. Вы самостоятельно пишете
конфигурацию, образы, DAG, Spark-программу и публикацию результата.

## Что предоставлено

В `data/sample.csv` находятся 11 116 строк Online Retail II; происхождение и
лицензия описаны в [data/README.md](data/README.md). Не заменяйте вход и
`SHA256SUMS`. Полный UCI архив скачивать не нужно. Интернет нужен при сборке
образов и зависимостей; после сборки обработка использует предоставленные данные.

[versions.json](versions.json) закрепляет образы по digest и основные библиотеки:
Airflow 2.10.5, Spark/PySpark 3.5.4, Python 3.12, Java 17, SeaweedFS 4.48,
Redis 7.4.2. PostgreSQL 16.6 служит базой метаданных Airflow. Для Python-зависимостей Airflow
предоставлен официальный `constraints.txt`. Устанавливая библиотеки в его образ,
оставляйте `apache-airflow==2.10.5` в требованиях, чтобы pip не изменил версию Airflow. Собственные зависимости также закрепите версиями.

Заготовка намеренно не запускается: `compose.yaml` содержит пустой список
сервисов, DAG не реализован, Spark-программа завершается `NotImplementedError`.
Готовое решение в шаблон не включено.

## Соберите среду в Compose

Обязательные имена сервисов:

| Сервис | Назначение |
|---|---|
| `postgres` | Метаданные Airflow |
| `airflow-init` | Миграция метаданных и локальная учётная запись; успешное завершение |
| `airflow-webserver` | Веб-интерфейс и API Airflow на внутреннем порту 8080 |
| `airflow-scheduler` | Планирование и выполнение задач DAG |
| `spark-master` | Spark master: порт 7077; внутренний веб-интерфейс 8080 |
| `spark-worker` | Минимум один зарегистрированный Spark worker |
| `seaweedfs` | S3-совместимое хранилище на внутреннем порту 8333 |
| `redis` | Признаки на внутреннем порту 6379 |

Названия Airflow следуют официальному Compose-примеру. Дополнительные сервисы
разрешены; Celery worker, broker и Flower для этой работы не обязательны.
Для выполнения DAG можно использовать LocalExecutor с PostgreSQL.
Для учебной среды достаточно `parallelism=2`: это ограничивает число процессов
и потребление памяти. Не выделяйте десятки executors для этой выборки.
На сервере весь проект получает 4 vCPU и 8 GiB памяти. Сборка и проверка
ограничены 45 минутами; рассчитывайте настройки сервисов на эти ресурсы.

Все основные компоненты подключены к стандартной сети `default` проекта.
Используйте имена сервисов для подключений, а не `localhost` другого контейнера.
Не задавайте `container_name`: Compose сам создаёт имена, позволяющие запускать
несколько проектов параллельно. Файлы и bind mounts находятся внутри `hw2/`;
постоянное состояние размещайте в именованных volumes своего проекта.

Добавьте healthcheck и зависимости готовности. Airflow запускается после готового
PostgreSQL и успешного `airflow-init`; простой старт контейнера не доказывает
готовность приложения. После подъёма не должны требоваться ручная установка
библиотек, миграция БД или создание подключений.

Параметры локального учебного доступа по умолчанию:

- Airflow API: user `airflow`, password `airflow`, Basic authentication.
- S3: access key `hw2-local`, secret key `hw2-local-only`, region `us-east-1`.
- Redis: без пароля внутри сети проекта.

Если вы меняете параметры для локальной работы, передавайте их через окружение
и опишите настройки в README. Персональные токены и учётные записи не нужны.

## Напишите DAG и Spark-программу

DAG ID: `online_retail_features`. `schedule=None`, без catchup. DAG должен быть
доступен и включён после старта среды, чтобы его можно было запустить вручную.
Airflow API располагается по `http://airflow-webserver:8080/api/v1` внутри проекта.

Обязательные задачи и зависимости:

```text
get_dataset → put_dataset → features_engineering → load_features
```

| Задача | Реальный результат |
|---|---|
| `get_dataset` | Прочитан предоставленный `sample.csv` и проверен хеш из `SHA256SUMS` |
| `put_dataset` | Исходные байты записаны в bucket `hw2`, key `input/sample.csv` |
| `features_engineering` | Ваш Spark-job читает CSV из S3, рассчитывает признаки и пишет Parquet в `hw2/features/` |
| `load_features` | Прочитан сохранённый Parquet; клиентские признаки записаны в Redis |

Дополнительные задачи допускаются. Каждый обязательный этап выполняет свою
работу; задачи-заглушки не заменяют процесс. Исключения не должны скрываться
за успешным состоянием DAG.

Spark-программа выполняется в кластере master/worker. У driver и workers
одинаковая версия Python. При самостоятельной сборке Spark настройте `SPARK_HOME`
и запускайте компоненты штатными средствами дистрибутива; наличие master UI
ещё не означает, что worker сможет запустить executor. Имя Spark application —
`online_retail_features`; для каждого запуска DAG создавайте отдельное приложение.
Весь расчёт выполняйте средствами Spark; `toPandas` и расчёт вместо Spark запрещены.
Подготовьте зависимости чтения/записи S3 при сборке образа, а не загрузкой
незакреплённых библиотек во время обработки. Разбиение на функции не фиксируется.

## Рассчитайте клиентские признаки

Оставьте строки с непустым `customer_id`, invoice без префикса `C` без учёта
регистра, `quantity > 0` и `unit_price > 0`. Пустой `description` не исключает
покупку. Не удаляйте одинаковые товарные строки автоматически.

В Parquet — одна строка на каждого оставшегося клиента, четыре поля в таком порядке:

| Поле | Spark type | Значение |
|---|---|---|
| `customer_id` | string | Идентификатор клиента |
| `order_count` | long | Число различных `invoice_id` |
| `total_amount` | decimal(20,6) | Сумма `quantity × unit_price` |
| `average_order_amount` | decimal(20,2) | Сумма / число заказов, half even |

Используйте цену decimal(20,6). Для half even подходит `bround`: 1.005 → 1.00,
1.015 → 1.02. Набор клиентов точный, без NULL и дублей.

Redis key — `hw2:customer:<customer_id>`. Значение — JSON с `order_count` как
числом, `total_amount` и `average_order_amount` как строками с фиксированной
точностью. `customer_id` внутри JSON допустим, но должен совпадать с ключом.

Повторный запуск на том же входе возвращает тот же результат: суммы не накапливаются,
старые части Parquet и устаревшие ключи этой работы не остаются в результате.

## Запуск и проверка

Из каталога `hw2/`:

```sh
docker compose up --build --wait
```

Откройте локальный веб-интерфейс Airflow и запустите DAG кнопкой Trigger DAG.
Для доступа с хоста публикуйте порт веб-интерфейса на `127.0.0.1`; номер порта
можно менять через окружение. Другие сервисы не требуют портов на хосте.

Локальная проверка из корня репозитория:

```sh
python3 hw2/check.py
```

Она создаёт отдельный Compose-проект, запускает ваш DAG дважды через API,
самостоятельно читает S3/Redis и сверяет результат. Завершив проверку, удаляет
только свой проект. Локальный PASS не означает серверного зачёта. Логи каждого прогона сохраняются в `hw2/output/` (этот каталог не сдаётся).
Дополнительные
Python-библиотеки на компьютере для запуска команды не нужны (достаточно Python 3.10+); проверяющий процесс
с зависимостями запускается в отдельном контейнере.

Остановить собственную среду из `hw2/`:

```sh
docker compose down
```

## Сдача

В корневом README своего проекта опишите компоненты, запуск, расчёт, места хранения
результата и повторный запуск. Сдайте весь `hw2/` вместе с README; `output/`, логи,
состояние volumes и секреты в Git не нужны.

Отправьте всё одним коммитом в `main`
зарегистрированного репозитория. Последняя строка сообщения — `MLSD-HW: HW2`.
Задание определяется по этому маркеру; проверяется точный SHA сдачи.

Базовые 10 баллов даются за работающий полный проект и правильный результат.
Ранний бонус — +3; OpenSpec — отдельные +2. Проверка кода доступна сейчас,
проверка OpenSpec будет включена отдельно. Её ожидание не задерживает оценку
кода. Если сдаёте OpenSpec, включите
собственные proposal/tasks/spec в тот же коммит. Оставьте один активный пакет
HW2, завершённый пакет HW1 перенесите в `openspec/changes/archive/`.

Сроки 2026, 18:00 МСК: ранний бонус строго до 12 октября, мягкий срок 19 октября,
жёсткий срок 26 октября.

## Что проверяет сервер

Собирает именно ваш проект; проверяет сервисы, исполнение DAG и два отдельных
Spark application; читает фактический CSV/Parquet из S3 и JSON из Redis; сравнивает
всех клиентов и агрегаты с независимым расчётом. После второго запуска проверяет
повторяемость. Dockerfile, DAG и публикацию не заменяет готовой реализацией.

Сбой проверяющей инфраструктуры — SYSTEM_ERROR; подтверждённая ошибка проекта —
FAILED. Локальный PASS подтверждает только локальную проверку; результат
сдачи подтверждает сервер курса.
