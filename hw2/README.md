# Домашняя работа 2. Подготовка клиентских признаков

## Цель задания

Подготовить признаки по клиентам из Online Retail II с помощью Spark, сохранить их в S3 и Redis и настроить запуск обработки через Airflow.

## Вам понадобятся

- Docker с Docker Compose v2, Linux/WSL/macOS.
- Python 3.10+ для запуска локальной проверки.
- Малый датасет из `hw2/data/sample.csv` — 11 116 строк, около 1 МБ.

На сервере работа проверяется на полном файле с теми же колонками. Скачивать его для разработки не нужно.

## Задача

В каталоге `hw2/` своего репозитория HW1 напишите:

- Dockerfile для Airflow и Spark с нужными библиотеками;
- конфигурацию Docker Compose;
- DAG Airflow;
- Spark-программу для расчёта признаков;
- загрузку рассчитанных признаков в Redis.

Версии компонентов, имена сервисов и параметры подключения приведены в [технической памятке](TECHNICAL.md).

### DAG

Создайте DAG `online_retail_features` с задачами:

1. `get_dataset` — чтение входного CSV. Локально это `hw2/data/sample.csv`; на сервере по этому же пути подаётся полный файл.
2. `put_dataset` — сохранение CSV в S3: bucket `hw2`, путь `input/sample.csv`.
3. `features_engineering` — чтение CSV из S3, расчёт признаков в Spark и сохранение Parquet в `hw2/features/`.
4. `load_features` — чтение Parquet и загрузка признаков в Redis.

Задачи выполняются в указанном порядке. Можно добавлять вспомогательные задачи. Не используйте заглушки. Расчёт через `toPandas` запрещён.

### Данные

| Поле | Содержимое |
|---|---|
| `invoice_id` | Номер заказа; префикс `C` обозначает отмену |
| `stock_code` | Код товара |
| `description` | Описание товара; может отсутствовать |
| `quantity` | Количество единиц товара, целое число |
| `invoice_at` | Дата и время заказа |
| `unit_price` | Цена единицы товара |
| `customer_id` | Идентификатор клиента; может отсутствовать |
| `country` | Страна |

Для расчёта оставьте строки с непустым `customer_id`, `quantity > 0` и `unit_price > 0`. Исключите заказы, номер которых начинается с `C` без учёта регистра. Пустое описание товара не исключает покупку. Одинаковые товарные строки автоматически удалять не нужно.

### Признаки

Для каждого клиента рассчитайте:

| Поле | Значение | Тип Spark |
|---|---|---|
| `customer_id` | Идентификатор клиента | string |
| `order_count` | Число различных `invoice_id` | long |
| `total_amount` | Сумма `quantity × unit_price` | decimal(20,6) |
| `average_order_amount` | Сумма покупок / число заказов | decimal(20,2) |

В Parquet должна быть одна строка на клиента, без NULL и повторов. Порядок полей — как в таблице.

Цену приведите к `decimal(20,6)`. Денежные значения не считайте через float/double. Средний чек округляйте методом half even: 1.005 → 1.00, 1.015 → 1.02. В Spark для этого есть `bround`.

В Redis используйте ключи `hw2:customer:<customer_id>`. Значение — JSON: `order_count` хранится числом, `total_amount` и `average_order_amount` — строками с шестью и двумя знаками после запятой. Поле `customer_id` внутри JSON допустимо, но должно совпадать с идентификатором в ключе.

Например, значение по ключу `hw2:customer:17`:

```json
{"order_count": 2, "total_amount": "13.000000", "average_order_amount": "6.50"}
```

## Условия и требования

- Всё собирается и запускается через Docker Compose без ручной настройки контейнеров.
- Spark работает в кластере: master и хотя бы один worker. Каждому запуску DAG соответствует новое Spark-приложение `online_retail_features`.
- Повторный запуск обновляет результаты: суммы не накапливаются, старые части Parquet и устаревшие ключи Redis удаляются.
- В корневом README описаны компоненты, запуск и места хранения результата. Описание HW1 сохраняется.
- Проект работает в пределах 4 vCPU и 8 GiB памяти. На сборку и проверку отводится 45 минут.

## Локальная проверка

Из корня репозитория выполните `sh check.sh HW2`.

Проверка собирает проект, дважды запускает DAG, проверяет работу Spark и сверяет признаки в S3 и Redis. Локально используется малый CSV, на сервере — полный. Сервер проверяет также клиентов, которых нет в малом файле.

Если проверка не прошла, прочитайте сообщение и логи в `hw2/output/`. Локальный `PASS` не заменяет серверную оценку.

## Формат сдачи

Отправьте каталог `hw2/` и корневой README в ветку `main` зарегистрированного репозитория. Последняя строка сообщения коммита — `MLSD-HW: HW2`. Других маркеров заданий в сообщении быть не должно. Логи, результаты расчёта, содержимое volumes и секреты в Git не нужны.

Результат проверки придёт в Telegram и появится на коммите в GitHub.

### OpenSpec: бонус +2

OpenSpec-пакет необязателен. Его можно отправить сразу или отдельно от кода. Проверка пакета начинается после зачёта кода; если код уже зачтён, повторно сдавать его не нужно.

Чекер ищет пакет в `openspec/changes/` от корня репозитория.

В `openspec/changes/<имя-изменения>/` должны быть:

- `proposal.md` — зачем нужны признаки и что меняется в проекте;
- `tasks.md` — список задач реализации и проверки;
- `specs/<capability>/spec.md` — требования и сценарии «WHEN … THEN …».

Для отправки используйте маркер `MLSD-HW: HW2`. Завершённый пакет HW1 перенесите в `openspec/changes/archive/`, оставив один активный пакет HW2.
