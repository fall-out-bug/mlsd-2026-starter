# Домашняя работа 1: воспроизводимый запуск сервиса в Docker

В этой работе нужно собрать небольшой сервис в Docker. Он должен отвечать
на запрос `GET /health` JSON-объектом, в котором есть поле `"status":"ok"`.
Другие поля в ответе допустимы. Язык и фреймворк выбираете вы.

## Как начать

Этот репозиторий создан из шаблона курса. Работайте в нём, в ветке `main`;
не используйте копию репозитория курса.

Нужны Git, Docker Desktop или Docker Engine с работающим фоновым процессом
(`daemon`), а также стандартные команды WSL/Linux: `sh`, `curl`, `awk`,
`grep`, `date`, `rm` и `timeout`. Проверьте Docker:

```sh
docker version
```

В выводе должны быть разделы Client и Server.

## Рекомендуемое окружение

Язык и стек — на ваш выбор. Если предпочтений нет, курс рекомендует:
**Python 3.12**, базовый образ **`python:3.12-slim`** (с дайджестом),
пакетный менеджер **`uv`** (файл зависимостей `uv.lock`) и **Docker
Engine или Docker Desktop** 24+ под WSL2/Linux. Сам `uv` попадает в
образ отдельной строкой `FROM` — закрепите и её дайджестом:

```dockerfile
FROM ghcr.io/astral-sh/uv@sha256:<дайджест>
FROM python:3.12-slim@sha256:<дайджест>
COPY --from=0 /uv /usr/local/bin/
```

## Что должно быть в репозитории

Добавьте в корень репозитория:

- `Dockerfile`. Каждая строка `FROM`, кроме `FROM scratch`, должна
  указывать образ с идентификатором содержимого (digest):
  `image@sha256:<64 символа>`. Он закрепляет точную версию базового
  образа. Узнать идентификатор уже скачанного образа можно так
  (результат целиком идёт в `FROM`):

  ```sh
  docker inspect --format '{{index .RepoDigests 0}}' python:3.12-slim
  ```

- Один файл закреплённых зависимостей: `uv.lock`, `poetry.lock`,
  `Pipfile.lock`, `requirements.lock`, `package-lock.json`,
  `npm-shrinkwrap.json`, `pnpm-lock.yaml`, `yarn.lock`, `Cargo.lock` или
  `go.sum`. Если зависимостей нет — файл всё равно нужен (например,
  минимальный `uv.lock` с одной строкой `version = 1`).
- Свой `README.md` с обычными командами сборки и запуска. В команде
  сборки контекст должен быть `.`, а в команде запуска должен быть порт
  `8080`.
- Сервис с `GET /health`. Он должен ответить за две секунды JSON-объектом
  с полем `"status":"ok"`.

Например, в вашем README могут быть такие команды:

```sh
docker build --tag hw1 .
docker run --publish 8080:8080 hw1
```

Docker Compose можно использовать дополнительно, но он не заменяет
`Dockerfile` и эти две команды.

## Структура репозитория: один живой проект

Этот репозиторий один на весь курс — единый проект, который от домашки к
домашке получает новые способности. Следующее задание расширяет уже
написанное: добавляет файлы и меняет существующие (`Dockerfile`, код,
этот `README.md`). Контрактные файлы каждого задания (те, что читает его
проверка) лежат в корне с именами из задания. Шаги развития системы
фиксируйте дельта-спецификациями в `openspec/changes/<имя>/`.


## Локальная проверка

Из корня репозитория выполните:

```sh
sh ./check.sh
```

Скрипт проверит обязательные файлы, соберёт образ, запустит контейнер,
обратится к `/health` и удалит созданные этим запуском контейнер и образ.
`PASS` означает только, что локальная проверка прошла. Не запускайте
скрипт в чужом недоверенном репозитории: команда сборки выполняет его код
на вашей машине.

Если видите `FAIL`, прочитайте сообщение, исправьте указанную проблему и
снова запустите `sh ./check.sh`. После исправления сдавайте заново новым
коммитом с сообщением `MLSD-HW: HW1` (см. ниже).

## Подключение к системе курса и сдача

После локального `PASS` подключите репозиторий к системе курса (один раз):
откройте **https://mlsd.beetles.family**, войдите через GitHub, установите
GitHub App курса для этого репозитория и привяжите Telegram — сайт
проведёт по шагам.

Затем сохраните работу и отправьте ветку:

```sh
git add .
git commit -m 'MLSD-HW: HW1'
git push origin main
```

Этот коммит помечает работу как HW1: после отправки сервер курса проверит
её сам. Результаты придут в Telegram и появятся на коммите. До подключения
репозитория к системе локальный `PASS` и отправка не подтверждают приём
работы или оценку.

## Бонус +3: OpenSpec-пакет

К базовым 10 баллам можно получить **+3 за OpenSpec-пакет** — описание
шага развития вашей системы. Он проверяется автоматически после успешной
базовой сдачи: отдельную отправку делать не нужно, система возьмёт
`openspec/changes/` из того же коммита.

1. Создайте каталог `openspec/changes/<имя-изменения>/` (например,
   `hw1-health-service`).
2. Внутри — три файла:
   - `proposal.md` — зачем изменение, что меняется, что не входит;
   - `tasks.md` — чек-лист задач;
   - `specs/<capability>/spec.md` — дельта-спецификация: Requirements и
     сценарии вида «WHEN … THEN …».
3. Запушьте вместе с работой.

Пакет читает LLM-рецензент: он решает, можно ли по описанию восстановить
замысел и принять изменение. Пишите так, чтобы человек, не видевший ваш
код, понял предложение; результат придёт в Telegram вместе с базовым.

## Сроки

Все времена московские (МСК). Срок сдачи определяется временем приёма
сервером (`received_at`) той версии работы, которая затем успешно
пройдёт проверку, а не временем окончания проверки.

| Событие | Момент | Правило |
|---|---|---|
| Выпуск задания | 21 сентября 2026, 18:00 | Задание объявлено на занятии L01. |
| Ранний срок | строго до 28 сентября 2026, 18:00 | Первая успешная отправка даёт бонус +2. |
| Мягкий срок | включительно 5 октября 2026, 18:00 | До него включительно базовая часть равна 10. |
| Жёсткий срок | 12 октября 2026, 18:00 | В этот момент и позже базовая часть равна 0. |

После мягкого срока за каждые полные 24 часа опоздания вычитается один
балл, но не ниже нуля. Подробности правил оценивания объявляются на
занятии и в канале курса.
