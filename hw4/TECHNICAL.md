# HW4. Технический контракт `hw4-serving-v1`

Публичная версия для starter. Условие работы — [README.md](README.md).

**Что это.** Публичный контракт HW4: что студент строит, как это запускается, какие данные входят, какие ответы выходят и что именно проверяет курс. Проверка работает только через этот контракт и не читает внутренности решения.

**Отношение к HW3.** HW4 — расширение проекта HW3, а не новый стенд. Сохраняются `postgres`, `mlflow`, `seaweedfs`, данные и артефакты HW3. Добавляются онлайн-фичестор, загрузчик, три сервиса применения и таблица активной версии.

**Статус.** Согласовано 09.11: значения раздела 13 фиксированы. До публикации остаётся проверить эталоном, что полный путь укладывается в 90 минут.

## 1. Что сдаётся

Один репозиторий, ветка `main`, последняя строка сообщения коммита — ровно `MLSD-HW: HW4`. Сервер проверяет полный SHA принятого push.

```text
hw4/
  compose.yaml
  service/
    gateway/            # публичный вход
    feature-service/    # выдача признаков из Redis
    model-service/      # применение модели из MLflow
  offline/
    feature-build/      # расчёт восьми признаков
    feature-loader/     # раскладка признаков в Redis
  config/
    models.json         # имена и версии моделей
  input/                # read-only вход, монтируется проверкой
  requirements.lock
  README.md
```

В Git не отправляются история, Parquet, модели, тома, логи и секреты. `hw4/README.md` описывает запуск, порты, переменные окружения и как восстановить активную версию.

## 2. Сервисы

Обязательные сервисы в `hw4/compose.yaml`:

| Сервис | Роль | Порт |
|---|---|---:|
| `gateway` | Публичный вход: «клиент + дата» → прогноз. Собирает ответ, отдаёт версию и дату | 8080 |
| `feature-service` | По «клиент + дата» отдаёт вектор восьми признаков из Redis | 8081 |
| `model-service` | По вектору и версии отдаёт вероятность; загружает модели из MLflow | 8082 |
| `feature-build` | Одноразовый расчёт признаков из истории в Parquet | — |
| `feature-loader` | Одноразовая раскладка Parquet в Redis | — |
| `redis` | Онлайн-фичестор | 6379 |
| `postgres` | Активная версия модели и журнал переключений; метаданные HW3 | 5432 |
| `mlflow` | Реестр моделей | 5000 |
| `seaweedfs` | Офлайн-таблицы признаков и артефакты | 8333 |

`airflow` и `spark` могут оставаться в проекте из HW3, но в обслуживании запросов не участвуют и проверкой HW4 не требуются.

Запуск:

```bash
cd hw4
docker compose up --build --wait
```

`feature-build` и `feature-loader` — одноразовые сервисы. `gateway` стартует после их успешного завершения. Повторный запуск загрузчика заменяет ключи для объявленных снимков, а не дописывает дубли.

## 3. Вход

Проверка монтирует read-only каталог `HW4_INPUT_DIR` в `/input`. В нём:

- `history.csv.gz` — нормализованная история с теми же восемью колонками, что в HW3: `invoice_id`, `stock_code`, `description`, `quantity`, `invoice_at`, `unit_price`, `customer_id`, `country`.
- `request.json` — объявленные снимки и параметры.

```json
{
  "contract_version": "hw4-serving-v1",
  "execution_id": "hw4_example_01",
  "dataset_version": "online-retail-ii-v1",
  "input_path": "history.csv.gz",
  "input_sha256": "<sha256>",
  "observed_from": "2009-12-01T00:00:00",
  "observed_until": "2011-12-09T00:00:00",
  "history_days": 90,
  "snapshots": [
    {"as_of": "2011-06-01T00:00:00", "split": "train"},
    {"as_of": "2011-09-01T00:00:00", "split": "validation"},
    {"as_of": "2011-11-01T00:00:00", "split": "test"}
  ]
}
```

Правила те же, что в HW3: период наблюдения полуоткрытый, время без пояса, выход окна за полноту истории отвергает запрос целиком.

## 4. Восемь признаков

Считаются на момент `as_of` по истории строго до этой даты.

| Признак | Тип | Правило |
|---|---|---|
| `order_count_90d` | int64 | Число разных счетов-покупок за 90 дней |
| `total_amount_90d` | decimal(20,6) | Сумма `quantity * unit_price` по покупкам за 90 дней |
| `average_order_amount_90d` | decimal(20,2) | `total / order_count`, half even; `0.00`, если заказов нет |
| `days_since_last_order` | int64 | Дней с последнего счёта-покупки; `-1`, если покупок не было |
| `distinct_stock_codes_90d` | int64 | Число разных `stock_code` среди покупок за 90 дней |
| `return_rate_90d` | decimal(10,6) | Отмены / (покупки + отмены) за 90 дней; `0`, если счетов нет |
| `order_count_30d` | int64 | Число разных счетов-покупок за 30 дней |
| `total_amount_30d` | decimal(20,6) | Сумма по покупкам за 30 дней |

Покупкой считается строка с `quantity > 0`, `unit_price > 0`, непустым `customer_id` и счётом, не начинающимся с `C`. Отменой считается счёт, начинающийся с `C`, с непустым `customer_id`. Строки без клиента в признаки не входят. Нулевая цена и нулевое количество не являются покупкой и не входят в знаменатель отмен. Дубли строк не удаляются.

## 5. Офлайн-сборка и загрузка

`feature-build` читает `/input/history.csv.gz` и `request.json`, считает восемь признаков для каждого объявленного снимка и пишет Parquet в `seaweedfs://hw4/offline/features/`:

| Поле | Тип |
|---|---|
| `client_id` | string |
| `as_of` | string, `YYYY-MM-DDTHH:MM:SS` |
| восемь признаков | по таблице выше |

Ключ — `(client_id, as_of)`, без пропусков и повторов. Пустой результат всё равно даёт читаемый Parquet с той же схемой.

`feature-loader` читает этот Parquet и раскладывает признаки в Redis. Ключ:

```text
hw4:features:<client_id>:<as_of>
```

Значение — JSON-объект с восемью признаками и `client_id`, `as_of`. Загрузчик заменяет значения для объявленных снимков. TTL не задаётся.

## 6. Модели в MLflow

Метки и разбиение — из HW3. Признаки — восемь из раздела 4. Обучаются две модели:

| Имя в MLflow | Семейство | Обязательность |
|---|---|---|
| `hw4-logistic` | логистическая регрессия | да |
| `hw4-boosting` | градиентный бустинг | да |

Выбор — по validation log loss по правилу HW3. В MLflow у каждой модели есть run с артефактами `pipeline.joblib`, `schema.json`, `manifest.json`. `manifest.json` перечисляет файлы и их SHA-256. `schema.json` перечисляет восемь признаков в порядке применения.

`model-service` загружает модель по паре `model_name` + `model_version`. Повторное обучение на запросе запрещено.

## 7. Активная версия

Состояние хранится в `postgres`, таблица `hw4.active_model`:

| Поле | Смысл |
|---|---|
| `model_name` | `hw4-logistic` или `hw4-boosting` |
| `model_version` | версия в MLflow |
| `activation_id` | идентификатор логической операции активации |
| `state_id` | идентификатор подтверждённого состояния |
| `activated_at` | время подтверждения |

`gateway` при старте читает активную версию и загружает её. Если записи нет — берёт `HW4_DEFAULT_MODEL` и `HW4_DEFAULT_VERSION`; если и их нет — стартует неготовым.

Активация: проверить модель в MLflow, загрузить, записать новую строку, вернуть `state_id`. Повтор с тем же `activation_id` возвращает тот же `state_id` и не создаёт второе изменение.

## 8. Эндпоинты

### gateway, 8080

`GET /health`

- `200` — активная модель загружена, `feature-service` и `model-service` доступны:
  `{"status":"ok","model_name":"...","model_version":"..."}`
- `503` — иначе: `{"status":"not_ready","reason":"..."}`

`POST /predict`

```json
{"client_id": "C1", "as_of": "2011-09-01"}
```

`200`:

```json
{
  "client_id": "C1",
  "as_of": "2011-09-01",
  "probability": 0.42,
  "model_name": "hw4-logistic",
  "model_version": "3",
  "feature_key": "hw4:features:C1:2011-09-01"
}
```

`POST /predict/batch`

```json
{"items": [{"client_id": "C1", "as_of": "2011-09-01"}, {"client_id": "C2", "as_of": "2011-09-01"}]}
```

`200` — результат на каждый элемент, порядок сохранён:

```json
{"results": [{"index": 0, "ok": true, "probability": 0.42, "model_name": "...", "model_version": "..."}, {"index": 1, "ok": false, "error": {"code": "feature_not_found", "message": "..."}}]}
```

Один пакет использует одну версию модели целиком.

`GET /model` — активная модель и `state_id`.

`POST /admin/activate`:

```json
{"model_name": "hw4-boosting", "model_version": "2", "activation_id": "op-123"}
```

### feature-service, 8081

`GET /features?client_id=C1&as_of=2011-09-01`

`200`:

```json
{"client_id": "C1", "as_of": "2011-09-01", "features": {"order_count_90d": 3, "total_amount_90d": 120.5, "...": "..."}}
```

`404` — ключа нет.

### model-service, 8082

`POST /predict`

```json
{"model_name": "hw4-logistic", "model_version": "3", "features": {"...": "..."}}
```

`200`: `{"probability": 0.42}`. `409` — модель несовместима со схемой.

## 9. Ошибки

Единый формат: `{"error": {"code": "...", "message": "..."}}`.

| Код | HTTP | Когда |
|---|---:|---|
| `invalid_request` | 400 | Нет поля, неверный тип или дата |
| `client_not_found` | 404 | Клиента нет в истории |
| `feature_not_found` | 404 | Нет ключа признаков на дату |
| `model_not_found` | 404 | Нет модели или версии в MLflow |
| `incompatible_model` | 409 | Схема модели не совпадает с признаками |
| `features_unavailable` | 503 | Redis или feature-service недоступны |
| `model_unavailable` | 503 | MLflow или model-service недоступны |
| `not_ready` | 503 | Нет активной модели |

## 10. Что проверяет курс

Проверка работает только через контракт.

1. **Контракт проекта.** Обязательные сервисы, порты, команды, схемы входа и ответов.
2. **Новые данные.** Кладёт свою историю и `request.json` в `HW4_INPUT_DIR`, запускает проект.
3. **Офлайн-путь.** Проверяет, что `feature-build` и `feature-loader` завершились, а ключи Redis соответствуют независимому расчёту восьми признаков.
4. **Онлайн-путь.** Спрашивает `feature-service` и `gateway`; сверяет вектор и вероятность с моделью студента, применённой к этому вектору.
5. **Версии.** Активирует вторую модель, проверяет видимость для новых запросов и сохранение выбора после перезапуска.
6. **Отказы.** Останавливает Redis, MLflow и model-service по очереди; проверяет объявленные ошибки и восстановление.
7. **Отчёт.** Прогоняет закреплённый набор случаев через `gateway`, считает покрытие, отказы, метрики и срезы. Отчёт — результат проверки, не сдача студента.
8. **Вердикт.** `PASSED`, `FAILED` или `SYSTEM_ERROR`; локальный `PASS` серверный зачёт не заменяет.

Проверка не импортирует код студента, не читает его внутренние таблицы и не загружает `pipeline.joblib` в доверенном observer. Модель студента применяется внутри изолированной гостевой среды.

## 11. Лимиты и сдача

- Ресурсы: **4 vCPU, 16 GiB, 90 минут** на сборку и полный путь; эталон ещё не прогнан.
- Пакет: не больше **128** элементов; **5 с** на элемент, **60 с** на пакет.
- Маркер: `MLSD-HW: HW4`; проверяется полный SHA принятого push.
- Даты: обычная оценка **16.11**, мягкий **23.11**, жёсткий **30.11**, 18:00 МСК.

## 12. Что остаётся решением студента

Структура кода, язык, библиотеки в рамках `requirements.lock`, способ расчёта признаков, формат внутренних модулей, механизм синхронизации версии, способ хранения состояния внутри объявленной таблицы. Контракт фиксирует только наблюдаемое поведение и артефакты.
