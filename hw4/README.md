# Домашняя работа 4. Онлайн-фичестор и сервис применения модели

В этой работе вы продолжаете проект HW3. Модель уже обучена и сохранена;
теперь она должна работать как сервис: принимать «клиент + дата», брать
признаки из онлайн-хранилища, применять выбранную версию модели и отвечать
вероятностью.

Полное [условие](TECHNICAL.md) задаёт сервисы, вход, восемь признаков, схему
Redis, модели в MLflow, эндпоинты, ошибки и лимиты. Стартер даёт условие,
маленькую историю и локальную проверку. Окружение и код вы создаёте сами.

## Что нужно реализовать

- `hw4/compose.yaml` с обязательными сервисами: `gateway`, `feature-service`,
  `model-service`, `feature-build`, `feature-loader`, `redis`, `postgres`,
  `mlflow`, `seaweedfs`.
- `feature-build` — расчёт восьми признаков из истории в Parquet.
- `feature-loader` — раскладка признаков в Redis по ключу
  `hw4:features:<client_id>:<as_of>`.
- `gateway` — публичный вход: `/health`, `/predict`, `/predict/batch`,
  `/model`, `/admin/activate`.
- `feature-service` — выдача вектора признаков из Redis.
- `model-service` — применение модели из MLflow по имени и версии.
- Две модели в MLflow: `hw4-logistic` и `hw4-boosting`.
- Таблицу активной версии в Postgres и восстановление выбора после перезапуска.
- Проверку версии на обязательной точке синхронизации `sync_token`:
  `POST /predict` с `sync_token`, `GET /admin/sync/<token>` и `POST /admin/sync`.
- `requirements.lock` и `README.md` с запуском и переменными окружения.

Порт на хост публикует только `gateway` (8080); остальные сервисы доступны
внутри сети проекта. Внутренняя структура модулей — на ваше усмотрение.
Контракт фиксирует только наблюдаемое поведение и артефакты.

## Данные

Маленькая история для локальной проверки лежит в `hw4/data/history.csv.gz`,
запрос — в `hw4/data/request.json`, ожидаемые признаки — в
`hw4/data/expected_features.json`. Это примеры форматов и границ, а не
канонический набор.

Полная история HW3 скачивается по инструкции HW3 и не хранится в Git.

## Запуск

```bash
cd hw4
docker compose up --build --wait
```

`feature-build` и `feature-loader` — одноразовые сервисы; `gateway` стартует
после их успешного завершения. Вход монтируется read-only в `/input`
через переменную `HW4_INPUT_DIR`.

## Проверка и сдача

```bash
sh check.sh HW4                # полная локальная проверка (нужен Docker)
python3 hw4/check.py --preflight-only   # только Compose-границы и вход
```

Локальная проверка сверяет границы Compose-проекта и вход (C1–C2), затем
поднимает проект и проходит по маленькой истории: завершение
`feature-build`/`feature-loader` (B1), ключи и значения в Redis (B3–B4),
`/health`, `/features`, `/predict` (S1–S3) и объявленные ошибки 404/404/400
(E1–E3). Для проверки `feature-service` локальная проверка запускает
одноразовый probe-контейнер в сети проекта.

Она не заменяет серверную: переключение версий, сохранение после перезапуска,
отказы зависимостей, отчёт и независимую сверку признаков и вероятностей
сервер выполняет сам. Локальный `PASS` серверный зачёт не заменяет.
Именованные тома после проверки сохраняются; полный сброс состояния —
`docker compose down -v`.
