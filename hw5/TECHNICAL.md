# HW5. Контракт `hw5-stream-v1`

HW5 продолжает проект HW4 на Online Retail II. Контракт HW4 сохраняется
с уточнениями признаков и классификации строк (§§3–4): все 14 сервисов,
офлайн-контур, модели и API остаются. Добавляются потоковый обработчик
транзакций, очередь заданий на прогноз с неизменяемыми результатами и
мониторинг данных, включая зрелые метки и оценку качества по сохранённым
прогнозам. Переобучения и выпуска новых моделей в HW5 нет: применяется
активная модель HW4.

## 1. Что сдаётся

Один репозиторий, ветка `main`, последняя строка сообщения коммита —
ровно `MLSD-HW: HW5`. `hw5/` —
самодостаточный проект, расширяющий HW4:

```text
hw5/
  compose.yaml
  service/
    gateway/
    feature-service/
    model-service/
    stream-worker/
    monitor/
  offline/
    feature-build/
    feature-loader/
  models/
    hw4-logistic/<version>/{pipeline.joblib, schema.json, manifest.json}
    hw4-boosting/<version>/{pipeline.joblib, schema.json, manifest.json}
  config/models.json
  data/            ← поставляется курсом: открытые сценарии и SCENARIOS.md
  versions.json    ← поставляется курсом: версии образов и библиотек
  requirements.lock
  README.md
  runbook.md
```

Каталог `models/` и файл `versions.json` уже есть в стартовом репозитории;
создавать их заново не нужно. Версия модели для
регистрации — имя каталога `<version>`. Проект регистрирует артефакты в
MLflow при инициализации с теми же именами и версиями; обучение не
запускается, повторный `docker compose up` не создаёт новых версий.
Первичную активацию выполняет проверка через `POST /admin/activate`;
до активации задания `ok` ожидают (§9).

## 2. Сервисы

Обязательны 16 сервисов, поднимаются одним `docker compose up`:

| Сервис | Назначение | Порт |
|---|---|---|
| `postgres` | состояние HW4, прогнозы, алерты (состояние потока — Postgres или Redis, §6) | внутри |
| `airflow-init` | инициализация Airflow (одноразово) | — |
| `airflow-webserver` | Airflow UI/API | внутри |
| `airflow-scheduler` | планировщик | внутри |
| `spark-master` | Spark | внутри |
| `spark-worker` | Spark | внутри |
| `seaweedfs` | Parquet и артефакты | внутри |
| `mlflow` | модели | внутри |
| `redis` | признаки HW4 + потоки Redis Streams | внутри |
| `gateway` | публичный вход | `8080` |
| `feature-service` | выдача признаков | `8081` |
| `model-service` | применение модели | `8082` |
| `stream-worker` | обработка потока и заданий | `8083` |
| `monitor` | мониторинг данных и алерты | `8084` |
| `feature-build` | сборка признаков (одноразово, exit 0) | — |
| `feature-loader` | загрузка признаков в Redis (одноразово, exit 0) | — |

Наружу публикуется только `gateway:8080`; порты 8081–8084 не публикуются.
Проверка присоединяется к сети Compose и обращается к сервисам по именам
(`stream-worker:8083`, `monitor:8084`, `redis:6379`). Локально студент
обращается к внутренним ручкам через `docker compose exec` — примеры в
`hw5/data/SCENARIOS.md`. Healthcheck обязателен у всех долгоживущих
сервисов. `gateway` стартует после успешной сборки и загрузки HW4;
`stream-worker` и `monitor` — после готовности `redis` и `postgres`.

После перезапуска контейнеров с сохранёнными томами должны сохраниться:
`now` и `closed_until`, идентичность и состояние
принятых событий, сохранённые прогнозы, зафиксированные выборы заданий,
журнал терминальных исходов и счётчики, алерты и их подтверждения,
активная версия HW4, записи и consumer groups Redis Streams. Начальные
значения из `request.json` применяются только к чистой среде. Способ
сохранения данных Redis выберите сами (например AOF или RDB); настройка
должна обеспечивать перечисленные гарантии при проверяемых остановках и
перезапусках.

Операционные метки времени (`at`, `opened_at`, `acked_at`, `paused_at`,
`created_at`) — настенное время UTC, ISO 8601; учебное время (`now`,
`closed_until`, `as_of`) — даты учебного сценария, не настенные часы.
`now` — текущий день сценария; `closed_until` — первый ещё не закрытый
день (события с днём `< closed_until` отвергаются, §5).

## 3. Базовый контур: признаки, модели, API

Базовый контур применения модели полностью определён ниже (это контракт
`hw4-serving-v1`; правила действуют и в офлайн-контуре, и в потоке HW5).

### 3.1. Вход офлайн-пути

`history.csv.gz` — история в схеме: `invoice_id`, `stock_code`,
`description`, `quantity`, `invoice_at` (ISO 8601 без часового пояса
`YYYY-MM-DDTHH:MM:SS`), `unit_price` (decimal-строка, шесть знаков),
`customer_id`, `country`. `request.json` задаёт снимки `as_of`, период
наблюдения и SHA-256 входа (§13). Проект читает вход и не изменяет его.

Покупка — `invoice_id` не начинается с `C` (без учёта регистра),
`quantity > 0` и `unit_price > 0`. Отмена — `invoice_id` начинается с `C`
(без учёта регистра), `quantity ≠ 0` и `unit_price ≠ 0`. Строки с нулевым
quantity или ценой не являются ни покупкой, ни отменой. Пустой
`customer_id` в признаки не входит.

### 3.2. Восемь признаков

На пару `client_id` + `as_of`. Окно 90 дней — время события в
`[as_of − 90 дней 00:00, as_of 00:00)`; короткое окно 30 дней — аналогично.
Популяция снимка — клиенты с хотя бы одним событием (покупка или отмена)
строго до `as_of`.

| Признак | Тип | Правило |
|---|---|---|
| `order_count_90d` | int | число различных `invoice_id` покупок в окне 90 дней |
| `total_amount_90d` | decimal(20,6) | сумма `quantity × unit_price` покупок окна 90 дней |
| `average_order_amount_90d` | decimal(20,2) | `total_amount_90d / order_count_90d`, half-even; `0.00` при нуле |
| `days_since_last_order` | int | календарных дней от последней покупки до `as_of`; `−1`, если покупок не было |
| `distinct_stock_codes_90d` | int | различных `stock_code` покупок окна 90 дней |
| `return_rate_90d` | decimal(10,6) | различные `invoice_id` отмен / (различные invoice покупок + различные invoice отмен) окна 90 дней; `0` при нулевом знаменателе |
| `order_count_30d` | int | число различных `invoice_id` покупок в окне 30 дней |
| `total_amount_30d` | decimal(20,6) | сумма `quantity × unit_price` покупок окна 30 дней |

Строки одного заказа не удваивают `order_count`; заказ выходит из окна
только после выхода последней своей строки. Суммы и `distinct_stock_codes`
считаются только по покупкам. Денежные значения — точные decimal,
округление half-even; не через float/double.

### 3.3. Офлайн-путь

`feature-build` (Airflow + Spark) собирает Parquet в `seaweedfs`:
`offline/features/features.parquet` — колонки `client_id`, `as_of` и восемь
признаков. `feature-loader` читает Parquet и пишет в Redis ключи
`hw4:features:<client_id>:<as_of>` со значением из восьми признаков.
Оба сервиса одноразовые (exit 0).

### 3.4. Модели

В MLflow ровно две модели: `hw4-logistic` и `hw4-boosting`. У каждой версии
артефакты `pipeline.joblib`, `schema.json` (восемь признаков в порядке
применения), `manifest.json` (файлы и их SHA-256). `model-service`
загружает модель по паре `model_name` + `model_version`. Повторное обучение
на запросе запрещено. В HW5 артефакты предоставлены в `models/` и
регистрируются при инициализации без обучения (§1).

### 3.5. Активная версия

Состояние — в `postgres`, таблица `hw4.active_model`: `model_name`,
`model_version`, `activation_id`, `state_id`, `activated_at`.
`POST /admin/activate` идемпотентен по `activation_id`: повтор с тем же
`activation_id` возвращает тот же `state_id` и не создаёт второго изменения.
Состояние переживает перезапуск контейнеров с сохранённым томом.

### 3.6. Эндпоинты базового контура

**gateway, 8080:**

- `GET /health` → `200 {"status": "ok", "model_name", "model_version"}`;
  `503 {"status": "not_ready"}`, пока активная версия недоступна.
- `POST /predict` `{"client_id", "as_of"}` → `200 {"client_id", "as_of",
  "probability", "model_name", "model_version", "feature_key"}`.
- `POST /predict/batch` `{"items": [...]}` → `200 {"results": [...]}`;
  порядок и длина совпадают с запросом, один `model_version` на пакет.
- `GET /model` → `200 {"model_name", "model_version", "activation_id",
  "state_id"}`.
- `POST /admin/activate` `{"model_name", "model_version", "activation_id"}`
  → `200 {"model_name", "model_version", "activation_id", "state_id"}`.

**feature-service, 8081:** `GET /features?client_id=...&as_of=YYYY-MM-DD` →
`200 {"client_id", "as_of", "features": {...}}`; `404`, если ключа нет.

**model-service, 8082:** `POST /predict` `{"model_name", "model_version",
"features": {...}}` → `200 {"probability"}`; `409`, если модель несовместима
со схемой.

### 3.7. Ошибки базового контура

Единый формат: `{"error": {"code", "message"}}`.

| Код | HTTP | Когда |
|---|---:|---|
| `invalid_request` | 400 | нет поля, неверный тип или дата |
| `client_not_found` | 404 | клиента нет в истории |
| `feature_not_found` | 404 | нет ключа признаков на дату |
| `model_not_found` | 404 | нет модели или версии в MLflow |
| `incompatible_model` | 409 | схема модели не совпадает с признаками |
| `features_unavailable` | 503 | Redis или feature-service недоступны |
| `model_unavailable` | 503 | MLflow или model-service недоступны |
| `not_ready` | 503 | активная версия ещё не готова |

## 4. Поток транзакций

Транспорт — Redis Streams в существующем сервисе `redis`. Имена фиксированы:

- `hw5:events` — транзакции;
- `hw5:requests` — задания на прогноз;
- consumer group `hw5-workers` на обоих потоках.

**Сериализация.** Проверка кладёт запись одним полем `payload`:
`XADD hw5:events * payload '<JSON события>'`; для `hw5:requests` —
аналогично. Потребитель читает поле `payload` и разбирает JSON.

**Создание групп.** `stream-worker` при старте создаёт потоки и группы
(`XGROUP CREATE ... MKSTREAM`) с начальным ID `0`; ошибка BUSYGROUP для
существующей группы игнорируется. Готовность к подаче — наличие группы
`hw5-workers` на обоих потоках (`XINFO GROUPS`); проверка ждёт готовности
перед первым `XADD`. Сообщения, добавленные до запуска worker, не
теряются: чтение с начала потока. Потоковый обработчик `stream-worker`
(далее — worker) получает записи каждого потока в
порядке возрастания ID: в этом порядке применяет события, а в потоке
заданий — принимает новые задания и сохраняет их признаки. Момент фиксации
пары модели — §7. Завершать задания можно не по порядку: ожидающее
`ok`-задание не блокирует завершение последующих (§9).
После перезапуска worker
забирает неподтверждённые записи прежнего потребителя (`XAUTOCLAIM` либо
`XPENDING` + `XCLAIM`).

Схема события (JSON, точный набор полей):

```json
{
  "event_id": "e-000123",
  "invoice_id": "I100",
  "stock_code": "S1",
  "description": "item",
  "quantity": 2,
  "invoice_at": "2011-11-20T10:00:00",
  "unit_price": "10.000000",
  "customer_id": "17850",
  "country": "GB"
}
```

Типы: строки — string; `quantity` — int; `unit_price` — decimal-строка с
шестью знаками; `invoice_at` — ISO 8601 без часового пояса
`YYYY-MM-DDTHH:MM:SS` (схема HW3). Лишние или отсутствующие поля, неверный
тип — отказ `invalid_event`. День события — дата `invoice_at`.

**Покупка и отмена.** Покупка — `invoice_id` не начинается с `C` (без
учёта регистра), `quantity > 0` и `unit_price > 0`. Отмена — `invoice_id`
начинается с `C` (без учёта регистра), `quantity ≠ 0` и `unit_price ≠ 0`. Строки с нулевым
quantity или ценой не являются ни покупкой, ни отменой и в агрегаты не
входят. Пустой `customer_id` — событие принимается, но не приписывается
клиенту (`unattributed`), в состояние клиентов не входит. Это уточнение
формулировки HW4 §4 (где условия покупки и отмены могли пересекаться);
поведение совпадает с оракулом HW4.

**Идентичность.** `event_id` стабилен для строки источника и не равен
`invoice_id`. Сравнение содержимого — по нормализованным значениям
объявленных полей: строки — как есть (посимвольно), `unit_price` — по
числовому значению, `quantity` — как целое, порядок ключей JSON не важен.
Порядок проверок фиксирован:

1. Схема: нарушение → отказ `invalid_event`.
2. Идентичность: известный `event_id` с тем же содержимым → `duplicate`
   (идемпотентно, состояние не меняется); известный `event_id` с другим
   содержимым → отказ `conflict`. Проверка идентичности выполняется **до**
   проверки закрытия: повтор ранее принятого события после закрытия его
   дня остаётся `duplicate`.
3. Закрытие: новый `event_id` с днём `< closed_until` → отказ `closed_past`.
4. Иначе событие принимается, в том числе с днём `> now`: событие из
   будущего сохраняется сразу; в окно признаков оно входит, только если его
   день лежит в этом окне (день `as_of` в окно не входит, §6).

Проверьте себя на событии `e-000123`: первая запись применена, но не
подтверждена. Что покажут `received_total` и `duplicates` после её
повторной доставки? А после нового `XADD` с тем же `payload`? Ответ — в
правиле терминальных исходов ниже.

**Терминальные исходы и счётчики.** Всякая запись потока получает
терминальный исход: принят, отклонён (`invalid_event`/`conflict`/
`closed_past`) или распознан как `duplicate`. Исход фиксируется в журнале
(ключ — ID записи потока) и запись подтверждается. Эффект применения,
фиксация `event_id`, счётчики и журнал изменяются как один логический
атомарный шаг (§6). Повторная доставка **той же записи** (тот же ID записи
потока) опознаётся по журналу и подтверждается без изменения счётчиков;
`duplicate` фиксируется только для **новой** записи потока с повторным
`event_id`. Счётчики считают логические сообщения (записи потока), не
физические доставки.

Общие счётчики имеют одинаковые имена в `/stream/status` и
`/monitor/report`; `non_purchase_rows` и `cancellations` присутствуют
только в `/monitor/report`:

```text
received_total = invalid_events + conflicts + closed_past_rejected
               + duplicates + unattributed + attributed_new
```

`attributed_new` — впервые принятые события с непустым `customer_id`.
`non_purchase_rows` и `cancellations` — подмножества `attributed_new`
(описательные, не слагаемые).

**Восстановление после отказа.** Журнал отказов позволяет найти исходную
запись по ID потока (`XRANGE`) и причину. `invalid_event` исправляется
повторной подачей корректного события; `conflict` — для нового содержимого
нужен новый `event_id`; `closed_past`
необратим в рамках прогона: `closed_until` монотонно не убывает. Инструкции по каждому
виду отказа — в `SCENARIOS.md`.

## 5. Учебное время и закрытие истории

Время задаёт проверка, не ОС. Начальные значения — из `request.json`:
`now = observed_from`, `closed_until = observed_from` (только для чистой
среды; далее сохраняются, §2).

`stream-worker`, 8083:

- `POST /admin/time {"now": "YYYY-MM-DD", "closed_until": "YYYY-MM-DD"}` →
  `200 {"now", "closed_until"}`. Обе величины монотонно не убывают;
  `closed_until ≤ now`; `closed_until ≤ observed_until` (исключительная
  граница покрытия данных, §13); нарушение → `400 invalid_request`.
  `now` может опережать `observed_until`.
- `GET /stream/status` →

```json
{
  "now": "2011-11-20",
  "closed_until": "2011-11-01",
  "events_pending": 0,
  "requests_pending": 0,
  "received_total": 123,
  "invalid_events": 0,
  "conflicts": 0,
  "closed_past_rejected": 0,
  "duplicates": 2,
  "unattributed": 5,
  "attributed_new": 116,
  "requests_invalid": 0,
  "requests_conflict": 0,
  "predictions_written": 4,
  "last_event_id": "1732000000000-0",
  "last_request_id": "1732000000005-0"
}
```

`events_pending` / `requests_pending` — число записей, доставленных группе,
но не подтверждённых (`XPENDING`). `received_total` — все логические
сообщения потока событий с терминальным исходом. `last_event_id` /
`last_request_id` — **непрерывная граница**: наибольший ID, до которого
все записи включительно доведены до терминального исхода (приняты,
отклонены или распознаны как duplicate). Начальное значение обоих полей
в чистой среде — `"0-0"`. Для пустого потока его часть условия границы
выполнена; общая граница определяется по обоим потокам и pending ниже.
Если
задание ещё ожидает результата, `last_request_id` не продвигается за его
запись, даже когда следующие задания уже завершены. События применяются
в порядке возрастания ID, поэтому граница событий непрерывна.

- `GET /stream/rejections?limit=N` →
  `{"rejections": [{"id", "kind": "event|request", "reason", "at"}]}`;
  порядок — новые сверху; `at` — настенное UTC (§2).

**Граница обработки.** Проверка фиксирует ID последних добавленных записей
каждого потока. Граница достигнута, когда `last_event_id` и
`last_request_id` не меньше этих ID **и** `events_pending = 0` и
`requests_pending = 0`. Один нулевой `XPENDING` границу не доказывает:
записи, ещё не доставленные группе, в pending не видны — поэтому требуется
и условие по `last_*_id`. Проверка продвигает время и закрытие **только на
достигнутой границе**; поэтому закрытие не обгоняет уже поданные события,
а эталон и зрелые метки (§11) полны по построению. Перед продвижением
`closed_until` до `W` проверка подаёт все предусмотренные сценарием
события с днём `< W` и ждёт границы обработки. **Задания на прогноз подаются
только после достижения границы по событиям** для всего поданного набора;
независимость от порядка (§15) относится к перестановкам внутри набора
событий, целиком обработанного до снимка.

Событие с днём `< closed_until` (новый `event_id`) отклоняется с причиной
`closed_past`: состояние и прошлые прогнозы не меняются, отказ наблюдаем.
До закрытия опоздавшие события (день в прошлом, но `≥ closed_until`)
принимаются.

## 6. Признаки и снимки в потоке

Те же восемь признаков и правила окна — §3.2. В потоке признаки считаются
из уже полученных событий; отмены учитываются в окне по дню самой отмены.

Единственный источник событий для потокового состояния — записи
`hw5:events`: на сервере их подаёт проверка, локально — студент по
сценариям. Сам проект не загружает файл событий напрямую;
`history.csv.gz` используется только офлайн-путём HW4 (двойной учёт
запрещён).

**Атомарность.** Применение события к состоянию, фиксация его `event_id`,
счётчики и журнал терминального исхода происходят как один логический
атомарный шаг (транзакция либо эквивалент). Сбой в любой точке между
получением и подтверждением после перезапуска приводит к ровно одному
применению и одному учёту: повторная доставка той же записи обязательна и
не удваивает агрегаты и счётчики. Механизм — на студенте; проверяется
поведение.

Состояние хранится постоянно (Postgres либо Redis с сохранённым томом) и
переживает перезапуск (§2).

## 7. Задания на прогноз

Элемент `hw5:requests` (поле `payload`):

```json
{"request_id": "r-000001", "client_id": "17850", "as_of": "2011-11-20"}
```

`request_id`, `client_id` — строки; `as_of` — строка `YYYY-MM-DD`.
Точный набор полей; отсутствие поля или нарушение формата →
`invalid_request`. Сравнение содержимого — строки как есть, порядок
ключей не важен.

**Три состояния `request_id`:** неизвестный; принятый (фиксация выбора
сохранена, результата ещё нет); завершённый (результат сохранён).
Порядок проверок:

1. Схема: нарушение → отказ `invalid_request`.
2. Идентичность принятого/завершённого `request_id`: то же содержимое →
   повтор идемпотентен (завершённый возвращает сохранённый результат,
   принятый продолжает обработку по сохранённому выбору). Новая запись
   потока с тем же ID и payload идемпотентна: worker распознаёт повтор, не
   создаёт второй результат, фиксирует терминальный исход записи и
   подтверждает её; результат доступен через `GET /predictions/{request_id}`.
   Повтор принятого, но ещё не завершённого задания подтверждается сразу
   (терминальный исход новой записи); исходная запись остаётся ожидающей
   до сохранения результата (§9).
   Другое содержимое → отказ `conflict`; сохранённый результат и выбор не
   меняются.
3. Новый `request_id`: `as_of` обязан совпадать с текущим `now`; иначе
   отказ `invalid_request`.

Редоставка задания с сохранённой фиксацией обрабатывается по сохранённому
выбору, даже если `now` продвинулся. Задание без фиксации обрабатывается
как новое (правило 3).

**Фиксация выбора.** При принятии нового задания worker фиксирует снимок
состояния полученных событий и сохраняет внутренний выбор, включая
вычисленные восемь признаков; пересчёт признаков после фиксации не
выполняется. Для исхода `ok` активная
пара модели фиксируется один раз для каждого задания — когда оно впервые
обнаруживает непустую активную версию (атомарное чтение `hw4.active_model`);
до этого задание ожидает с зафиксированными признаками (§9). Выбор
(признаки, а для `ok` — и пара) сохраняется до вызова модели; повторные
попытки и редоставки используют сохранённый выбор. Поздние события не
меняют сохранённые признаки.

Исходы:

| Условие | Исход |
|---|---|
| у клиента нет полученных событий строго до `as_of` | `status: "no_history"` |
| у клиента нет покупок в окне `[as_of − 90d, as_of)` | `status: "no_history"` |
| иначе | `status: "ok"`: зафиксированные признаки → `model-service` с зафиксированной парой → вероятность |

`no_history` не требует вызова модели и сохраняется; редоставка возвращает
сохранённый результат (п. 2). Полный вид результата (оба исхода пишутся в Postgres
`hw5.predictions` **до подтверждения задания** и неизменяемы):

```json
{
  "request_id": "r-000001",
  "client_id": "17850",
  "as_of": "2011-11-20",
  "status": "ok",
  "features": {"order_count_90d": 3, "total_amount_90d": "120.000000",
               "average_order_amount_90d": "40.00", "days_since_last_order": 2,
               "distinct_stock_codes_90d": 3, "return_rate_90d": "0.000000",
               "order_count_30d": 1, "total_amount_30d": "40.000000"},
  "model_name": "hw4-logistic",
  "model_version": "1",
  "probability": 0.412345,
  "educational_now": "2011-11-20",
  "created_at": "2026-11-23T18:05:00Z"
}
```

В опубликованном результате `no_history` поля `features`, `model_name`,
`model_version`, `probability` равны `null` (внутренний выбор признаков для
`no_history` не сохраняется); остальные поля заполнены. `probability` — JSON-число (float);
сравнение с независимым расчётом — допуск `1e-9` (конвенция настоящей проверки).
Позднейшие покупки не меняют сохранённый `no_history`; новый `request_id`
даёт новый результат.

Чтение: gateway `GET /predictions/{request_id}`:

- `200` сохранённый JSON — завершённый;
- `200 {"request_id": "...", "status": "pending"}` — принятый, результат
  ещё не сохранён (не является сохранённым прогнозом);
- `404 prediction_not_found` — `request_id` не принят.

Повторное вычисление до подтверждения допустимо только с сохранённым
выбором; потеря принятого задания или дублирование опубликованного
результата — нет. Один логический результат на `request_id`.

## 8. Контрольные точки остановки

`stream-worker`, 8083:

- `POST /admin/pause` — два варианта тела:
  `{"point": "after_receive", "kind": "event|request"}` и
  `{"point": "<другая точка>"}` (без `kind`). Ответ `200 {"armed", "kind"}`
  возвращается сразу: точка остановки установлена. Обработчик остановится,
  когда до неё дойдёт подходящая запись; проверить, произошла ли остановка,
  можно через `GET /admin/pause`.
- `GET /admin/pause` → `{"armed", "kind", "paused_at", "detail"}`;
- `POST /admin/resume` → `200`.

Объявленные точки:

| Точка | kind | Где останавливается worker | Что видит проверка |
|---|---|---|---|
| `after_receive` | event или request | после получения записи из очереди, до обработки | запись в `XPENDING`, состояние ещё не изменено |
| `after_state_write` | event | после атомарного применения события, до подтверждения | событие в состоянии, запись в `XPENDING` не подтверждена |
| `after_choice_write` | request | после сохранения фиксации выбора, до вызова модели | выбор в хранилище, прогноза ещё нет, задание в `XPENDING` |
| `after_result_write_before_ack` | request | после записи результата прогноза, до подтверждения задания | прогноз в Postgres, задание в `XPENDING` не подтверждено |

Для `after_receive` поле `kind` обязательно; для остальных точек `kind`
не передаётся (переданное лишнее поле игнорируется). Точка
`after_choice_write` применяется к заданиям `ok`: срабатывает после
сохранения полной фиксации (признаки + пара), до вызова модели; если
активной версии ещё нет — после появления версии и сохранения пары.
Задания `no_history` эту точку не проходят (вызова модели нет). Worker
останавливается на первой подходящей записи, достигшей точки (для
`after_receive` тип задаётся полем `kind`, для остальных — таблицей выше); `detail` содержит
ID записи потока и `event_id`/`request_id`. Срабатывание однократное: после
остановки точка разряжается; `resume` продолжает обработку. Пауза
останавливает worker целиком. Состояние `armed`/`paused_at` живёт в памяти
процесса и **не переживает перезапуск**: после рестарта worker обрабатывает
поток обычно.

Проверка использует точки для сценариев отказа: видит внешнее состояние и
неподтверждённую запись, затем завершает процесс (SIGKILL) и перезапускает
его на тех же томах. В сценариях восстановления проверка не меняет вход и
время между остановкой и перезапуском. Примеры вызова — в
`hw5/data/SCENARIOS.md`.

## 9. Недоступность модели

Проверка временно блокирует соединение `stream-worker` → `model-service`,
затем восстанавливает. Правило относится к заданиям, которым нужен вызов
модели (исход `ok`): задание остаётся ожидающим (`requests_pending ≥ 1`),
результат не записан, фиктивной вероятности и ложного успеха нет; worker
повторяет попытки **не приостанавливая обработку других записей** — события и
задания `no_history` обрабатываются обычно и во время блокировки. После
восстановления — ровно один правильный результат с зафиксированным выбором
(§7). Если активная версия ещё не выбрана, задания `ok` ожидают так же,
с уже зафиксированными признаками. Подтверждение задания: исходную запись подтверждайте только после
сохранения результата; новую запись с тем же `request_id` и содержимым —
по правилу повтора (§7).

## 10. Переключение версии посреди потока

`POST /admin/activate` (§3.6) допустим в любой момент, включая
время обработки потока. Момент упорядочивания — фиксация пары модели (§7):
задания, чья пара зафиксирована после активации, используют новую версию;
задания с парой, зафиксированной до активации, сохраняют свою версию и
вероятность, даже если результат записан позже. После появления активной
версии каждое ожидающее задание фиксирует текущую пару при первом успешном
чтении; последующие активации сохранённую пару не меняют. Уже сохранённые
прогнозы неизменны. Идемпотентность
активации и сохранение активной версии после перезапуска — HW4;
сохранение выбора задания — §§2 и 7 настоящего контракта.

## 11. Мониторинг данных

`monitor`, 8084: `GET /health`, `GET /monitor/report`,
`GET /monitor/alerts`, `POST /monitor/alerts/{id}/ack`.

`GET /monitor/report` → JSON:

```json
{
  "now": "2011-11-20",
  "closed_until": "2011-11-01",
  "input_quality": {
    "received_total": 1000, "invalid_events": 5, "conflicts": 1,
    "closed_past_rejected": 2, "duplicates": 3, "unattributed": 90,
    "attributed_new": 899, "non_purchase_rows": 40, "cancellations": 12,
    "since_last_advance": {"received": 60, "invalid_events": 4}
  },
  "drift": {
    "status": "ok|insufficient_data|drift",
    "statistic": 0.05, "threshold": 0.20, "min_observations": 200,
    "reference": {"from": "2011-06-03", "until": "2011-09-01", "n": 800,
                  "bins": [0.4, 0.3, 0.2, 0.08, 0.02], "frozen": true},
    "current": {"n": 800, "bins": [0.35, 0.3, 0.22, 0.1, 0.03]}
  },
  "predictions": {
    "total": 50, "ok": 44, "no_history": 6,
    "by_version": {"hw4-logistic": {"1": {"count": 44, "mean_probability": 0.40,
                   "histogram": [10, 12, 9, 8, 5]}}}
  },
  "stream_health": {
    "events_pending": 0, "requests_pending": 0,
    "oldest_pending_idle_seconds": 0
  },
  "labels": {"matured": 20, "immature": 24},
  "quality": {
    "by_version": {"hw4-logistic": {"1": {"n": 20, "log_loss": 0.51,
                   "roc_auc": 0.74, "status": "ok|not_assessed"}}}
  }
}
```

Числовые поля отчёта — JSON-числа; сравнение с независимым расчётом —
допуск `1e-9`. `statistic` равен `null`, только если пуст эталон или текущая выборка
(`n = 0`); при `0 < n < 200` статистика вычисляется, но статус
`insufficient_data`.

**Три популяции (три разных правила включения клиента).**

- Офлайн-снимок HW4: клиенты с хотя бы одной покупкой или отменой строго
  до `as_of` (правило HW4; нулевые и непокупочные строки не считаются).
  Клиент только с непокупочной строкой в офлайн-снимок не входит, но
  входит в популяцию сдвига.
- Исход прогноза: `no_history`, если нет полученных событий строго до
  `as_of` или нет покупок в окне (§7).
- Сдвиг: клиенты с хотя бы одним **приписанным принятым** событием строго
  до даты расчёта. Сюда входят клиенты только с отменами, только с
  непокупочными строками и только с давними покупками; их `order_count_90d`
  может быть 0 — интервал `[0]`. Отсутствие покупок в окне не исключает
  клиента из популяции сдвига.

**Сдвиг входов.** Величина — `order_count_90d`. Интервалы: `[0]`, `[1]`,
`[2–3]`, `[4–7]`, `[8+]`. Эталон — распределение на `reference_until` по
событиям с днём `< reference_until`, полученным к моменту расчёта;
`reference_from = reference_until − 90 дней` (нижняя граница окна,
справочная). До заморозки эталон **предварительный**: `n`, `bins` и
`statistic` вычисляются по уже полученным событиям и могут меняться от
допустимых опозданий; `frozen: false`, `status` ∈ {`ok`,
`insufficient_data`}, алерт `drift` не создаётся. Эталон заморожен
(`frozen: true`), когда `closed_until ≥ reference_until`; закрытие
происходит на границе обработки (§5), поэтому эталон полон и далее не
меняется. После заморозки `status` ∈ {`ok`, `insufficient_data`, `drift`}.
Текущее — распределение на `now` по принятым к моменту отчёта событиям.
Статистика — half L1-расстояние `0.5 · Σ |p_i − q_i|` ∈ [0, 1]. Порог
**0.20**; минимум **200 клиентов** в каждом периоде.

Алерт `drift` означает расхождение наблюдаемых долей интервалов
`order_count_90d` с эталоном — **не** доказательство падения качества и не
свидетельство статистической значимости: доли интервалов не содержат пар «сохранённая
вероятность — фактический исход». Качество оценивается отдельно по зрелым
меткам.

**Гистограмма предсказаний:** 5 интервалов `[0, 0.2)`, `[0.2, 0.4)`,
`[0.4, 0.6)`, `[0.6, 0.8)`, `[0.8, 1.0]` (последняя включает 1.0).

**Зрелые метки и качество.** Для каждого сохранённого прогноза `ok` на
дату `t`: метка = 1, если есть полученная **покупка** клиента (правила
§4) с днём в `[t, t + 30 дней)`, иначе 0. Метка зрелая только когда
**одновременно** `now ≥ t + 30 дней` и `closed_until ≥ t + 30 дней`.
Смысл условий разный: `now` — завершение горизонта по календарю,
`closed_until` — полнота данных для этого горизонта; в этом контракте
второе гарантирует первое (`closed_until ≤ now`), но опасная реализация —
проверять только `now` или ставить `0`, пока горизонт не закрыт. Если
после закрытия горизонта покупки в нём нет, метка равна `0`; до закрытия
прогноз не входит в оценку. Незрелые исключаются из оценки, не обнуляются. Так как
`closed_until ≤ observed_until`, прогнозы с `t + 30 > observed_until` в
этом прогоне не созревают и исключаются. Качество — накопительно по всем
сохранённым `ok` с начала прогона; единица наблюдения — один сохранённый
`request_id` (повторы не добавляют наблюдение, `no_history` не участвует).
Метрики по **сохранённым** вероятностям: log loss (клиппинг
`[1e-12, 1 − 1e-12]`) и ROC-AUC (ничьи — половинный вклад)
в разрезе версий модели. Разрезы описательные: версии могли обслуживать
разные даты и клиентов, это не сравнение моделей на общем наборе. Пустой
или одноклассовый набор зрелых — `status: "not_assessed"`, обе метрики
`null`, не ноль.

**Алерты.** `GET /monitor/alerts` → `{"alerts": [...]}`, новые сверху.
Хранятся в Postgres (`hw5.alerts`), переживают перезапуск:

```json
{"id": "drift-2011-11-20", "kind": "drift", "severity": "critical",
 "reason": "half_l1=0.31>=0.20", "opened_at": "2026-11-23T18:10:00Z",
 "status": "open|acknowledged", "acked_at": null}
```

Формат `id` — на усмотрение студента; требуется уникальность и
стабильность (повторный ack по тому же id). `reason` фиксируется при
открытии.

| Kind | Правило срабатывания | Severity | Повторное открытие после ack |
|---|---|---|---|
| `drift` | `frozen: true` и `statistic ≥ 0.20` и оба `n ≥ 200` | critical | если условие всё ещё истинно на следующей проверке |
| `input_quality` | `since_last_advance.received ≥ 20` и доля `invalid_events` в нём ≥ 5% | warning | в новом окне после сброса, если условие истинно |
| `event_conflict` | курсор отказов `conflict` ушёл вперёд относительно последнего алерта | warning | один новый алерт, если курсор ушёл вперёд после ack |
| `stream_lag` | `oldest_pending_idle_seconds ≥ 120` (максимум по обоим потокам) | warning | если условие всё ещё истинно на следующей проверке |

`input_quality` оценивается только при закрытии окна — успешном
`POST /admin/time`, изменившем `now` или `closed_until`;
`GET /monitor/report` показывает счётчики, но не открывает `input_quality`.
Остальные kind оцениваются и при таком продвижении, и при каждом
`GET /monitor/report`; вызов с неизменными значениями окно не сбрасывает
и `input_quality` не оценивает. Пока алерт данного kind открыт, новые
записи того же kind не создаются. После ack повторное истинное
условие создаёт **новый** алерт с новым `id`; прежний алерт остаётся
`acknowledged` и в `open` не возвращается. Для `event_conflict` счётчик — сумма отказов `conflict` событий и заданий
(`conflicts + requests_conflict`). При открытии алерта сохраняется текущее
значение счётчика; пока алерт открыт, новые записи того же kind не
создаются; после ack следующая проверка сравнивает счётчик с сохранённым и
создаёт не более одного нового алерта, если он вырос (несколько конфликтов
между проверками дают один алерт). `since_last_advance`
сбрасывается при каждом успешном `POST /admin/time`, изменившем `now` или
`closed_until`; повторный вызов с теми же значениями окно не сбрасывает.
Порядок при продвижении: оценить закрывающееся окно `input_quality`
(открыть алерт, если условие выполнено) → обнулить счётчики окна →
применить новые `now`/`closed_until` → оценить `drift`, `stream_lag`,
`event_conflict` по новому состоянию. Оценку алертов выполняет monitor;
worker инициирует её при успешном изменении времени (до ответа на
`POST /admin/time`), monitor также оценивает при чтении отчёта.
Алерт `stream_lag` во время пауз и недоступности модели возможен и ложным
не считается.

`POST /monitor/alerts/{id}/ack` → `200` полный объект алерта после
изменения (`status: "acknowledged"`, заполненный `acked_at`); повтор
возвращает тот же `acked_at`; неизвестный id → `404 alert_not_found`.
Проверка вызывает ack от лица оператора.

`runbook.md` обязателен в сдаче, с разделами «Алерты», «Реакция»,
«Эскалация». Структура проверяется локально; содержание машиной не
оценивается.

## 12. Ошибки

Формат и таблица ошибок базового контура — §3.7. Поток добавляет:

| Код | HTTP | Когда |
|---|---:|---|
| `prediction_not_found` | 404 | `request_id` не принят |
| `alert_not_found` | 404 | нет алерта по id |

Отказы событий (`invalid_event`, `conflict`, `closed_past`) и заданий
(`invalid_request`, `conflict`) наблюдаются через `/stream/rejections` и
счётчики `/stream/status`.

## 13. Вход

Курс кладёт в `HW5_INPUT_DIR` (read-only `/input`):

- `history.csv.gz` — история в схеме HW3 для офлайн-пути HW4;
- `request.json` — схема HW4 плюс поля потока:

```json
{
  "contract_version": "hw5-stream-v1",
  "execution_id": "...",
  "dataset_version": "...",
  "input_path": "history.csv.gz",
  "input_sha256": "...",
  "observed_from": "2011-06-01T00:00:00",
  "observed_until": "2011-12-10T00:00:00",
  "history_days": 90,
  "horizon_days": 30,
  "reference_from": "2011-06-03T00:00:00",
  "reference_until": "2011-09-01T00:00:00",
  "snapshots": [{"as_of": "2011-09-01T00:00:00", "split": "train"},
                {"as_of": "2011-12-01T00:00:00", "split": "test"}]
}
```

`snapshots` — даты офлайн-сборки HW4 (feature-build/loader строят ключи
`hw4:features:<client_id>:<as_of>` ровно на эти даты). `observed_until` —
**исключительная** граница покрытия: проверка подаёт события с днём
`< observed_until` и не закрывает дни `≥ observed_until`
(`closed_until ≤ observed_until`). Горизонт прогноза `[t, t + 30)` целиком
покрыт и может созреть, когда `t + 30 ≤ observed_until`. Поток событий и
заданий подаётся проверкой в Redis Streams; проект не читает события из
файлов и не изменяет вход.

## 14. Ресурсы и время

**4 vCPU, 16 GiB, 120 минут** на сборку и полный путь: от `docker compose up`
до завершения потоковых сценариев проверки, включая циклы остановки/
перезапуска и ожидание недоступности модели. Лимиты нужны для ограниченного
запуска. Лимиты ограничивают ресурсы прогонов проверки; скорость сверх
лимита не измеряется и на оценку не влияет.

## 15. Локальная проверка и открытые примеры

`sh check.sh HW5` — структура проекта и малый сквозной сценарий на
toy-данных. При FAIL скрипт указывает, какая проверка не прошла, и
показывает ожидаемый и фактический результаты либо подсказывает, где
найти диагностику. Локальный PASS не заменяет серверный зачёт.

`hw5/data/scenarios/` — малые открытые последовательности **всех классов
сценариев** с ожидаемыми результатами. В `hw5/data/SCENARIOS.md` для каждого класса указаны: исходное состояние, команды подачи и наблюдения (включая
`docker compose exec` для внутренних ручек), проверяемые промежуточные и
итоговые наблюдения, действие при расхождении, запуск из чистой среды и
повторный запуск без случайной потери данных. Классы: агрегаты и границы
окон, дубликаты и конфликты, старение, опоздания, закрытие, события из
будущего, `no_history`, настоящий вызов модели, восстановление в четырёх
точках, недоступность модели, переключение посреди потока, независимость
от порядка, мониторинг и алерты, зрелость меток и качество.

Отдельные требования к примерам:

- **Настоящий вызов модели:** не менее двух различающихся наборов
  признаков для одной фиксированной версии с независимо рассчитанными
  вероятностями (курс даёт ожидаемые значения в `expected.json`,
  рассчитанные оракулом) и сравнение с допуском `1e-9`; один из примеров
  использует незнакомый клиентский ID. Переключение версии — дополнительная проверка.
  Локальная проверка должна отклонять константную подмену вместо инференса
  (в том числе одну константу на версию), показывая ожидаемое и фактическое
  значения.
- **Восстановление после отказа:** для каждого вида отказа — поиск
  исходной записи по ID потока (`XRANGE`), допустимый следующий шаг
  (новый `event_id` для нового содержимого; закрытие необратимо).
- **Зрелость меток, изменённые условия:** сценарий с `now ≥ t + 30`, но
  `closed_until < t + 30` (метка незрелая), затем закрытие горизонта;
  покупки ровно в `t` (входит) и ровно в `t + 30` (не входит); ожидаемые
  метка и статус до и после закрытия. Студент определяет исход до
  просмотра ответа.
- **Независимость сигналов:** сдвиг при отсутствии зрелых меток (drift-алерт
  есть, качество `not_assessed`) и оценка на зрелом двухклассовом наборе
  без сдвига (метрики совпадают с независимым расчётом, drift-алерта нет).
  К каждому сценарию — вопрос для самостоятельного ответа и ориентиры
  самопроверки, размещённые отдельно от вопроса: наблюдаемый факт,
  недопустимый вывод, разумное следующее действие. При сдвиге без зрелых
  меток нельзя объявлять падение качества доказанным; при оценке без
  сдвига — делать причинное сравнение версий на разных популяциях.
  Ориентиры не являются машинным критерием.

Закрытая часть меняет идентификаторы, суммы, даты и порядок доставки
**внутри объявленных правил**; скрытых требований нет.

## 16. Сдача и сроки

Ветка `main`, маркер `MLSD-HW: HW5`. Версии образов и библиотек —
`hw5/versions.json` (наследуются HW4; новых внешних компонентов нет).

- выдача: **23 ноября 2026, 21:00 МСК**;
- ранний бонус +3: строго до **30 ноября 18:00 МСК** (начало практики L10);
- мягкий срок: **7 декабря 18:00 МСК** — 10 баллов, далее −1 за каждые
  полные 24 часа;
- жёсткий срок: **14 декабря 18:00 МСК** — 0;
- OpenSpec-бонус +2 — дополнительный пакет `openspec/changes/` по правилам
  курса (как в HW1–HW4); инструкция публикуется отдельным этапом
  **до 24 ноября 21:00 МСК**. До подключения сдача принимается без бонуса.

Серверная проверка запускается из version-pinned контура; версия контракта
`hw5-stream-v1` и версия checker сохраняются в результате. Контракт
заморожен с момента публикации и не меняется до жёсткого срока; исправление
ошибки checker не превращает проходившую сдачу в fail.
