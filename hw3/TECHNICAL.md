# HW3 · Технический контракт сдачи и артефактов

Версия контракта: **`hw3-temporal-v1`**, 24.10.2026.
Дополнение к [условию HW3](HW3.md). Ниже фиксируется поведение для реализации
проекта и проверки. Локальная команда HW3 входит в starter; серверный worker
проверяет принятую сдачу. Наличие документа не заменяет запуск проверки.
Обычная оценка начинается 2 ноября в 18:00 МСК, мягкий дедлайн — 9 ноября в
18:00 МСК, жёсткий — 16 ноября в 18:00 МСК.

## 1. Что сдаётся через Git

В зарегистрированный репозиторий, ветку `main`, студент отправляет:

| Объект | Содержание |
| --- | --- |
| `hw3/compose.yaml`, Dockerfiles | Самостоятельно собираемое и запускаемое окружение |
| Код решения (внутри `hw3/`) | Spark-расчёт примеров, обучение, выбор, оценка, применение комплекта. Структура каталогов и модулей — на усмотрение студента; код вызывается задачами DAG по разделу 4 |
| `hw3/airflow/dags/` | DAG `online_retail_training` |
| `hw3/config/candidates.json` | Объявленные конфигурации сравнения, включая константу, логистическую регрессию и дерево |
| `hw3/requirements.lock` | Точные версии Python-зависимостей расчёта/обучения/загрузки, включая транзитивные |
| `hw3/README.md` | Состав среды, запуск, пути результатов, объяснение обработки и настроек, как восстановить выбранный комплект |
| Корневой `README.md` | Ссылка на HW3 с сохранением описаний HW1–HW2 |

Последняя строка сообщения коммита — ровно `MLSD-HW: HW3`; других маркеров
домашек в сообщении нет. Сервер проверяет принятый полный SHA этого push,
а не более поздний HEAD ветки. Проверку не запускает простое изменение файла без корректной сдачи.

В Git не отправляются CSV истории, Parquet, модели, MLflow backend, volumes,
логи, `.env` с секретами и результаты запусков. Стартер должен предоставить
загрузку проверенной версии данных и `.gitignore`. Код не скачивает историю
или зависимости во время расчёта: всё готовится до его начала.
Файлы HW1/HW2, их пути и контракты сохраняются. HW3 не читает готовые агрегаты
Redis HW2 и не заменяет его выходы. Все файлы сборки HW3 находятся внутри `hw3/`.

`hw3/README.md` описывает решения и способ воспроизведения; автоматически
вычисленная таблица результатов хранится среди артефактов запуска. Студент
может дополнить README обсуждением своего локального результата, но сервер
не считает эти числа источником истины и не требует коммитить обученную модель.

## 2. Среда и основной путь

HW3 продолжает проект HW2: Airflow управляет этапами, Spark строит временные
примеры, S3 хранит результаты. Добавляется **MLflow tracking server**.
Обязательны сервисы `postgres`, `airflow-init`, `airflow-webserver`,
`airflow-scheduler`, `spark-master`, `spark-worker`, `seaweedfs`, `mlflow`.
Redis для HW3 не обязателен; контракт HW2 от этого не меняется.

Базовые версии Airflow/Spark/Python/Java и образы PostgreSQL/SeaweedFS
наследуются из [закреплённого HW2 versions.json](https://github.com/fall-out-bug/mlsd-2026-starter/blob/37938ef0aba24d04470c12e3446f94cf27b253af/hw2/versions.json).
MLflow, scikit-learn, NumPy, SciPy, pandas, joblib и остальные добавленные
зависимости студент закрепляет точными версиями в lock. Одинаковый lock
используется для обучения, проверочного обучения и загрузки. Это не обещание
совместимости моделей между разными версиями библиотек. Внешние образы
закрепляются digest; учебные примеры курса должны содержать проверенный
совместимый набор ML-зависимостей до выдачи.

Соединения внутри Compose — по именам сервисов в сети проекта. MLflow доступен
внутри по `http://mlflow:5000`, S3 — `http://seaweedfs:8333`, Airflow API —
`http://airflow-webserver:8080/api/v1`. Локальные учётные данные фиксированы
контрактом: Airflow `hw3` / `local-hw3-only`, S3 `local-hw3` / `local-hw3-only`;
доступ к внешнему MLflow не требуется.
Данные MLflow и S3 переживают перезапуск сервисов в volumes текущего проекта.
Зависимости, миграции, bucket и подключения создаются без ручной настройки.

Основной DAG: `online_retail_training`, `schedule=None`, без catchup,
`max_active_runs=1`.
Обязательные этапы с этими task IDs и достижимостью в указанном порядке:

`stage_input → build_examples → train_select → evaluate → publish`

Дополнительные задачи разрешены. Ошибка обязательного этапа не превращается
в успешный DAG. На каждый запуск нужен новый Spark application
`online_retail_training`; master должен иметь живой worker.
Окна, отбор, денежные агрегаты и метки вычисляются Spark средствами.
Передача уже агрегированных нескольких тысяч примеров в pandas/NumPy
для scikit-learn разрешена; выгружать исходные товарные строки и считать
временные примеры вместо Spark запрещено. Успешное Spark-приложение само
по себе не доказывает, что весь расчёт выполнен в Spark.

Проверка использует ресурсный профиль HW2: **4 vCPU, 8 GiB, 45 минут на
сборку и полный путь проверки**. Проект должен укладываться в эти границы,
включая ОС гостя и Docker; время работы не является метрикой качества модели.

## 3. Вход запуска

Курс подаёт входной CSV gzip и `request.json` в read-only каталог `/input`.
Путь и содержимое берутся из запроса; имя файла не является признаком
«публичный/закрытый тест». Все относительные пути в запросе разрешаются
от `/input`. Штатный запрос использует данные и календарь из HW3.md.
Для небольших проверок курс меняет данные, даты и объявленное наблюдение,
сохраняя те же 90/30 дней и схему; решение не должно зашивать список клиентов.

```json
{
  "contract_version": "hw3-temporal-v1",
  "execution_id": "hw3_example_01",
  "submission_sha": "<полный SHA сдачи>",
  "dataset_version": "online-retail-ii-v1",
  "input_path": "online-retail-ii-v1.csv.gz",
  "input_sha256": "7056f47bf85d8217cb3e5b71a815e75f3917feddd4a9c3f2da29a42c586706ad",
  "observed_from": "2009-12-01T00:00:00",
  "observed_until": "2011-12-09T00:00:00",
  "history_days": 90,
  "horizon_days": 30,
  "snapshots": [
    {"as_of": "2011-06-01T00:00:00", "split": "train"},
    {"as_of": "2011-09-01T00:00:00", "split": "validation"},
    {"as_of": "2011-11-01T00:00:00", "split": "test"}
  ]
}
```

`execution_id` — уникальный ID попытки DAG, ASCII `[A-Za-z0-9_-]{1,64}`.
Его задаёт инициатор; checker также задаёт фактический SHA. Airflow Trigger DAG
получает `dag_run_id`, равный `execution_id`, и `conf` вида
`{"request_path":"/input/request.json"}`. DAG читает запрос по этому пути,
проверяет совпадение ID и передаёт контекст стадиям. Стадия `stage_input`
проверяет хеш и сохраняет точную копию входа в S3. Период наблюдения полуоткрытый,
время не имеет пояса. При выходе любого окна за полноту `build` отвергает
весь запрос с кодом `INCOMPLETE_OBSERVATION`, не создавая готовый результат.
Для проверки `build` допустим запрос с одним снимком; полный DAG требует
ровно train/validation/test и зрелых меток предыдущего этапа.

## 4. Контракты стадий

Оркестрацию задаёт DAG из раздела 2: пять обязательных задач и их порядок.
Структура кода решения — модули, пакеты, имена файлов — на усмотрение
студента; контракт фиксирует только наблюдаемые входы и выходы каждой
стадии. Все вычисления выполняются внутри собранного проекта, на образе
с lock HW3.

| Стадия | Вход | Обязательный выход |
| --- | --- | --- |
| `stage_input` | `request.json` и CSV истории из `/input` | `runs/<execution_id>/input/` по разделу 3 |
| `build_examples` | история и объявленные окна | `examples/{train,validation,test}` + `manifest.json` по разделу 5 |
| `train_select` | только `examples/train`, `examples/validation` и `config/candidates.json` | `selection/` по разделу 6: `experiments.json`, `validation_predictions.parquet`, `validation_metrics.json`, `selected.json`, `bundle/` |
| `evaluate` | зафиксированные `selection/` и `examples/test` | `evaluation/`: `test_predictions.parquet`, `test_metrics.json` |
| `publish` | `evaluation/` | `result.json`, указатель `current.json`, метки MLflow по разделу 8 |

Метаданные запуска передаются задачам через переменные `HW3_EXECUTION_ID`,
`HW3_SUBMISSION_SHA`, `HW3_DATASET_VERSION`, `HW3_INPUT_SHA256` и
`MLFLOW_TRACKING_URI`. Окружение не заменяет доверенную копию этих
значений у проверяющего.

Повторный запуск стадии с теми же входами заменяет логический результат,
не дописывает строки; порядок строк/part-файлов Parquet произволен.
`train_select` сортирует train по `(as_of, customer_id)` перед fit,
фиксирует seed 2026 и число потоков численных библиотек в 1. Validation
сортируется так же для воспроизводимости.

`train_select` не использует test и не читает сырой журнал, другие части
или старые результаты: обучается только на train, выбирает только по
validation. Доступ к MLflow нужен для записи эксперимента, но не для
получения сторонних обучающих данных. `evaluate` не вызывает fit и не
меняет `selected.json`, файлы комплекта или validation-результат.

### Конфигурации и создание модели

`candidates.json` — JSON-массив объектов с полями `experiment_id`, `family`,
`preprocessing`, `estimator_params`. `family` принимает `constant`, `logistic`,
`tree`. `experiment_id` — стабильное уникальное имя ASCII, не MLflow run ID.
Список неизменен внутри запуска. Ровно одна константа с `experiment_id="constant"`,
минимум по одному кандидату `logistic` и `tree`. У константы
`preprocessing=[]`, `estimator_params={}`.

`preprocessing` — список шагов `{name, class, params}` в порядке применения;
`class` — полное имя класса, `params` — его аргументы. Допустимы
`sklearn.preprocessing.StandardScaler`, `MinMaxScaler`, `MaxAbsScaler`,
`RobustScaler` и `FunctionTransformer` из того же модуля. Это разрешённые
варианты, а не требование использовать каждый; отсутствие обработки допустимо.
Для `FunctionTransformer` допускаются отсутствие функции или `numpy.log1p`,
в JSON обозначенные `null` или строкой `numpy.log1p`. Собственные классы,
лямбды и замыкания в сериализуемой модели не используются: комплект должен
загружаться со стандартными зависимостями. Пустой список допустим.
`estimator_params` — настройки LogisticRegression/DecisionTreeClassifier;
они не должны менять зафиксированные ограничения HW3.

Конструирование пайплайна из конфигурации — обычная функция кода
решения (файл и имя — на усмотрение студента): она только собирает
объект из конфигурации, не читает файлы/данные, не обращается к сети,
не обучает модель. Последний шаг пайплайна — настоящий
`sklearn.linear_model.LogisticRegression` или
`sklearn.tree.DecisionTreeClassifier` соответствующего семейства.
Для всех поддерживающих его компонентов фактический `random_state=2026`;
отсутствие в config означает подстановку 2026, другое значение или None
недопустимы. Это отражается в `resolved_params` артефактов, не только
в тегах. Ключи и метки в Pipeline не передаются: вход — DataFrame
с тремя признаками в порядке ниже, каждый `float64`, полученный после
точного decimal-агрегирования.

Проверка сверяет объявленные конфигурации с артефактами `selection/`
и независимо пересчитывает метрики и правило выбора по разделу 6.

## 5. Схемы таблиц

Требуется Parquet со следующими полями в указанном порядке. Даты-ключи
сохраняются строками ISO 8601, всегда `YYYY-MM-DDTHH:MM:SS`, без пояса;
это исключает неявное преобразование даты клиента при чтении разными средствами.

**`examples/{train,validation,test}/`**:

| Поле | Тип | Ограничение |
| --- | --- | --- |
| `customer_id` | string | Непустой |
| `as_of` | string | Каноническая дата соответствующего снимка |
| `order_count` | int64 | Положительное число |
| `total_amount` | decimal(20,6) | Положительная сумма |
| `average_order_amount` | decimal(20,2) | Точный результат half even; может округлиться в 0 |
| `label` | int64 | 0 или 1 |
| `split` | string | `train`, `validation` или `test` |

Нет NULL и повторов `(customer_id, as_of)` во всём результате.
Каталог и значение `split` совпадают. Пустая таблица в контрольных сценариях
всё равно имеет читаемый Parquet-файл с той же схемой. Физическое разбиение Parquet произвольно;
дублирующие колонки разделов не добавляются. Признаки и деньги сверяются точно,
а не с допуском float. Одна дата не относится к двум частям.

**`validation_predictions.parquet` / `test_predictions.parquet`**:

| Поле | Тип |
| --- | --- |
| `experiment_id` | string |
| `customer_id` | string |
| `as_of` | string |
| `split` | string |
| `label` | int64 |
| `probability` | float64 |
| `in_slice` | bool |

Ключ — `(experiment_id, customer_id, as_of, split)`. Для каждого оценённого
кандидата ключи совпадают с соответствующей частью, без пропусков и лишних
строк. `in_slice` пересчитывается из истинного `order_count = 1`, а не
принимается на веру. Вероятность относится к **классу 1**; значение не округляется
для показа, конечно и лежит в `[0,1]`. JSON и Parquet не содержат NaN/Infinity.

Validation содержит прогноз каждого объявленного кандидата. Test — выбранного
и константы. Если выбрана константа, её прогнозы сохраняются один раз;
две роли сравнения в метриках ссылаются на одни строки.

## 6. JSON-артефакты

JSON — UTF-8, объектные ключи без повторов, конечные числа; отсутствие метрики
обозначается `null`. Неопределённость не кодируется строкой `NaN` или нулём.

| Файл | Обязательные поля |
| --- | --- |
| `experiments.json` | `contract_version`, `execution_id`, `submission_sha`, `dataset_version`, `input_sha256`, `candidates` |
| Элемент `candidates` | `experiment_id`, `family`, исходный `config`, `resolved_params` (включая defaults), `mlflow_run_id`, `status="FINISHED"` |
| `validation_metrics.json` и `test_metrics.json` | `contract_version`, `execution_id`, `records` |
| Элемент `records` | `experiment_id`, `role`, `split`, `group`, `n`, `n_positive`, `log_loss`, `roc_auc`, `log_loss_reason`, `roc_auc_reason` |
| `selected.json` | `contract_version`, `execution_id`, `submission_sha`, `dataset_version`, `input_sha256`, `experiment_id`, `family`, `mlflow_run_id`, `validation_log_loss`, `p_train`, `model_id`, `selection_rule="validation_log_loss_v1"` |
| `bundle/manifest.json` | `contract_version`, `model_id`, `family`, `files` — список `{path, sha256}` |

`resolved_params` имеет форму `{"pipeline": [{"name": "имя шага", "class": "полное имя класса", "params": {}}]}`.
Шаги перечислены в порядке Pipeline. Имя класса —
`type(step).__module__ + "." + type(step).__name__`; `params` содержит **все**
параметры `step.get_params(deep=False)`, включая defaults закреплённой библиотеки.
Строки, числа, bool и `None` переходят в соответствующие JSON-значения;
кортежи и списки — в массивы, словари со строковыми ключами — в объекты
(правило применяется рекурсивно). NumPy-скаляры преобразуются в Python-скаляры,
а разрешённая функция `np.log1p` записывается строкой `"numpy.log1p"`.
Не используйте `repr` объектов или адреса памяти.
Статус `FINISHED` означает успешное обучение и оценку, не просто наличие run.
Объявленные для текущего сравнения кандидаты должны завершиться успешно;
ранние неудачные эксперименты в MLflow не входят в этот список.

Для validation `role="candidate"`, `group="all"`, одна запись на кандидата.
Для test — четыре записи: роли `selected` и `baseline`, каждая для групп
`all` и `order_count_eq_1`. В обеих ролях допустим одинаковый `experiment_id`,
если выбрана константа. Уникальность метрик — по роли/кандидату/части/группе.

Причины отсутствия метрик: `empty_group` для обеих при `n=0`, `single_class`
только для ROC-AUC при непустой группе с одним классом; в остальных случаях
соответствующее поле причины — `null`. `n` и `n_positive` — целые числа,
`0 <= n_positive <= n`. Определённые метрики — конечные числа: log loss ≥ 0,
ROC-AUC в `[0,1]`. `n_positive` — число единиц, веса
примеров не используются. Формулы, clipping, правило равенства и допуски
определены в HW3.md и не меняются в checker.

## 7. Комплект модели и применение

Для выбранного варианта сохраняются:

```text
bundle/
  manifest.json
  schema.json
  requirements.lock
  pipeline.joblib
```

`pipeline.joblib` — обученный sklearn Pipeline с обработкой и классификатором.
Для выбранной константы — Pipeline с обученным `DummyClassifier(strategy="prior")`,
который даёт именно `p_train`; особый сервис/класс для константы не нужен.
Это способ упаковки константы, не дополнительный обучаемый кандидат.

`schema.json` содержит `schema_version="hw3-features-v1"`, упорядоченный
`features=[{name, source_type, model_type}]`, `positive_class=1`.
Имена: `order_count`, `total_amount`, `average_order_amount`;
`source_type`: `int64`, `decimal(20,6)`, `decimal(20,2)`;
`model_type` каждого — `float64`. Перед predict decimal-значения переводятся
в float64 ровно один раз; обученная обработка уже находится внутри Pipeline.
В `requirements.lock` — тот же набор зависимостей, что при обучении.

`model_id` — SHA-256 UTF-8 JSON списка `files`, отсортированного по `path`;
для сериализации используются `sort_keys=True`, `separators=(",", ":")`,
`ensure_ascii=True`, без перевода строки. В список входят ровно три файла:
`pipeline.joblib`, `requirements.lock`, `schema.json`. `manifest.json`
не хеширует сам себя. Метаданные MLflow и execution ID не входят в эту идентичность.
Изменение любого из трёх файлов меняет `model_id`.

Применение комплекта — часть задачи `evaluate`: она загружает bundle
в отдельном процессе, строит test-прогнозы из загруженного комплекта
и записывает `evaluation/test_predictions.parquet`. Так комплект остаётся
работающим артефактом, а не приложенным файлом. При загрузке порядок
признаков модели определяется `schema.json`. Доступ к CSV, таблицам train
и S3 при применении комплекта не требуется; HTTP-сервис инференса
остаётся HW4.

Полная упаковка обязательна только для выбранного кандидата. Развёртывание,
Model Registry, модельный сервер MLflow, ONNX и сравнение производительности
не требуются. Загрузка joblib выполняется только в изолированной среде
студенческого запуска: сериализованный объект является исполняемым входом.

## 8. MLflow, S3 и повторный запуск

MLflow experiment: `hw3`. Один parent run на `execution_id`, отдельный child run
на каждый кандидат. Теги связывают `contract_version`, `execution_id`,
`submission_sha`, `dataset_version`, `input_sha256`, `experiment_id`, `family`,
seed 2026 и родительский run. Параметры включают конфигурацию и даты/окна. В рамках текущей попытки
ровно один parent по `(contract_version, execution_id, submission_sha)`
и ровно один child каждого `experiment_id` с конечным статусом FINISHED;
также проверяется отсутствие дополнительных child этого кандидата в этом
исполнении. Повтор стадии возобновляет связанные run IDs и заменяет их
артефакты. История скалярных значений MLflow может содержать повторные записи:
проверяются последние значения и канонические JSON/Parquet-артефакты.

Каждый child хранит `config.json`, validation-прогнозы своего кандидата и
validation-метрики. В выбранном child дополнительно сохраняется полный
`bundle/`. Parent хранит `request.json`, `experiments.json`, `selected.json`,
обе таблицы метрик и test-прогнозы. Неопределённая метрика не отправляется
как scalar MLflow; её `null` и причина остаются в JSON. Test-метрики scalar
различаются префиксами роли/группы, например `test.selected.all.log_loss`.
Версия MLflow выбирается lock, вызовы API студент подбирает по её документации.

В S3 используется отдельный bucket **`hw3`**:

```text
runs/<execution_id>/
  input/input.csv.gz
  input/request.json
  examples/train/ ... validation/ ... test/
  selection/experiments.json
  selection/validation_predictions.parquet
  selection/validation_metrics.json
  selection/selected.json
  selection/bundle/...
  evaluation/test_predictions.parquet
  evaluation/test_metrics.json
  result.json
current.json
```

В `result.json`: `contract_version`, `execution_id`, `submission_sha`,
`input_sha256`, `model_id`, `parent_mlflow_run_id`, `status="ready"`,
список относительных `{path, sha256}` всех файлов результата, кроме самого
`result.json`; присутствуют все перечисленные выше входы и выходы.
`current.json` содержит `execution_id`, `result_uri`, SHA-256 байтов
`result.json`. URI — `s3://hw3/runs/<execution_id>/result.json`.

`publish` копирует уже выбранный комплект и проверенные результаты, не
переобучает модель. Сначала все файлы и `result.json`, затем одним объектом
заменяется `current.json`. При неуспехе новый ready-результат не появляется,
указатель предыдущего успешного исполнения не выдаётся за результат нового.

Повтор с новым `execution_id` создаёт новую историю и обновляет указатель;
старые успешные MLflow runs не удаляются. Повтор стадии в том же исполнении
заменяет её артефакты и использует те же связанные run IDs, не добавляет
дубликаты. Лишние старые part-файлы своего результата должны исчезнуть.
Нельзя очищать bucket/experiment целиком. Байтовая идентичность моделей
между переобучениями не требуется; выбор, ключи, метрики и вероятности
повторяются в объявленных допусках. Между freeze выбора и evaluate байты
комплекта, напротив, не меняются.

## 9. Автоматическая проверка и ошибки

Сервер использует принадлежащий курсу checker, свой вход и собственный
пересчёт ожидаемых результатов; студенческий `PASS` не является доказательством.
Проверяется полный путь и отдельно его части на маленьких историях.

| Проверка | Наблюдаемое условие |
| --- | --- |
| Сборка и DAG | Из принятого SHA запускается проект, обязательные задачи завершились, есть новый Spark application и доступные сервисы |
| История и признаки | Точные ключи, типы, границы, Decimal-агрегаты и метки совпали с независимым расчётом |
| Допустимость информации | Изменение будущего относительно одного снимка не меняет его прошлые признаки и популяцию |
| Обучение кандидатов | Каждый объявленный в `config/candidates.json` кандидат присутствует в `selection/experiments.json` с той же конфигурацией; validation-прогнозы и метрики пересчитываются по опубликованным артефактам |
| Выбор | Проверяющий заново считает validation log loss и применяет правило равенства ко всем кандидатам |
| Test | Test-прогнозы относятся к выбранному кандидату; независимый пересчёт четырёх метрик совпадает с отчётом |
| MLflow и S3 | Runs, параметры, прогнозы, комплект, указатель и SHA относятся к одному исполнению и принятой сдаче |
| Комплект | Bundle, его манифест, схема и `model_id` согласованы с выбранным кандидатом; test-прогнозы и метрики согласованы с опубликованными артефактами и независимым пересчётом |
| Повтор | Нет дубликатов/остаточных part-файлов; указатель ведёт на новое успешное исполнение; данные HW2 не затронуты |

Контрольные истории включают правую/левую границу, будущего клиента, отсутствие
будущей покупки, отмены, пустое описание, повтор товарной строки, денежное
округление, неполное наблюдение, пустой срез и один класс в оценке.
Для `train-select` непустой train с двумя классами обязателен; иначе понятный
отказ `TRAIN_SINGLE_CLASS` или `EMPTY_TRAIN`. Непустой validation обязателен;
при его отсутствии — `EMPTY_VALIDATION`. Непустой test и его срез могут
содержать один класс; пустой test допускается в отдельной проверке evaluate
и даёт четыре записи неопределённых метрик с `n=0`. Для основного входа
все части непусты и оба класса уже подтверждены.

Стадия завершается успехом или понятным отказом; для отвергнутого входа
артефакты запуска фиксируют `error_code` и короткое `message`:
`INPUT_HASH_MISMATCH`, `INVALID_REQUEST`, `INCOMPLETE_OBSERVATION`,
`EMPTY_TRAIN`, `TRAIN_SINGLE_CLASS`, `EMPTY_VALIDATION`, `INVALID_BUNDLE`.
При ошибке нельзя публиковать новый ready. Проверка ожидаемого отказа
считается успешным сценарием checker, а не незачётом.

Итог приёмки: `PASSED`, `FAILED` (воспроизводимое нарушение контракта решения),
`SYSTEM_ERROR` (невозможно установить результат из-за инфраструктуры курса).
Сбой получения данных, запуска доверенного observer или его окружения
не превращается в ошибку студента. Причина результата связывается с SHA,
версией контракта и конкретным сценарием, без скрытого порога качества.

Локальная команда — **`sh check.sh HW3`** из корня репозитория.
Она проверяет Compose, запускает DAG на опубликованной маленькой истории,
сверяет примеры с `data/expected.json`, хеши артефактов, повтор и сохранность
хранилищ. Диагностика сохраняется в `hw3/output/`. `data/SCENARIOS.md`
содержит открытые иллюстрации самостоятельной проверки обучения и комплекта.
Сервер запускает весь проект на выбранных закрытых историях и проверяет
опубликованные артефакты по этому контракту; он не обязан запускать каждый
открытый сценарий буквально. Локальный PASS не является серверным зачётом.

Проверки подтверждают наблюдаемое выполнение DAG, целостность и согласованность
артефактов, а также повторяемость результата при повторе запуска. Они не
переобучают модель с нуля и не загружают bundle отдельной пробой вне DAG,
поэтому сами по себе не доказывают подлинность обучения или загрузки модели.
Это не отменяет
требование раздела 7: задача `evaluate` применяет выбранный bundle в отдельном
процессе и записывает test-прогнозы. Как и раньше, проверки не доказывают, что
человек никогда не смотрел на открытый test; MLflow-теги или файл модели этого
тоже не доказывают. Закрытая история может проверять результат, но не добавляет
новых требований.

## 10. Граница окружения стартера

Окружение вы собираете сами по разделу 2; проверяются только границы и
наблюдаемые артефакты контракта. Сервисы должны использовать одну внутреннюю
Compose-сеть проекта без host ports. `HW3_INPUT_DIR` задаёт единственный
допустимый внешний каталог: bind `/input` только read-only — так проверяющий
передаёт вход; он должен быть доступен Airflow и Spark worker. Как переносить
рабочие данные между стадиями (том проекта или объектное хранилище), вы
решаете сами. Имена томов/сетей принадлежат Compose project. Host socket,
привилегированные режимы, внешние тома/сети и сетевые aliases запрещены;
`hostname` сервиса разрешён.

Сборка получает зависимости до запуска; во время сборки доступ в сеть есть,
но сервер собирает образы **classic builder'ом Docker**: Dockerfile обязан
собираться без расширений BuildKit — heredoc-синтаксис (`RUN <<EOF`,
`RUN python - <<'PY'`), `RUN --mount=`, `COPY --link` не поддерживаются
и молча ломают шаг. Проверьте сборку с `DOCKER_BUILDKIT=0` перед сдачей.
Загрузки в шагах сборки полезно завершать проверкой наличия файла, чтобы
молчаливое падение ломало сборку, а не запуск. На этапе вычисления сеть
изолирована от Интернета. Checker назначает свои имена проекта/образов и
передаёт вход после сборки. Он очищает только ресурсы своего запуска.
Локальные учебные учётные данные Airflow: `hw3` / `local-hw3-only`;
S3: `local-hw3` / `local-hw3-only`. Они не являются паролями какого-либо
внешнего сервиса.
