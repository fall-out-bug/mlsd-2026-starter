# Маленькие сценарии для самостоятельной проверки HW3

Это публичные примеры наблюдаемого результата. Они уточняют контракт, но не
дают порядок Spark-преобразований, код обучения или конфигурацию кандидатов.
Полная история и дополнительные сценарии остаются у курса.

## Временные примеры

`probes/temporal-base.csv.gz`, `probes/temporal-base-request.json` и
`probes/temporal-base-expected.json` — полный маленький сценарий. В train
есть восемь строк и оба класса; в validation — пять строк; в test — одна.
Он проверяет включение левой и исключение правой границы, зрелую отрицательную
метку, появление клиента только после события в истории, отмены, пустое и
многострочное описание, повтор товарной строки и half-even округление.

В частности, строка `boundary` на train имеет `total_amount="4.000000"` и
`label=1`: два события лежат по разные стороны `as_of`. Точное множество всех
строк находится в JSON, поэтому локальный checker сопоставляет результат, а
не пытается угадать его по отчёту.

## Обучение и выбор

Минимальная допустимая входная таблица train для `train-select` должна иметь
хотя бы одну строку `label=0` и хотя бы одну `label=1`; validation должна быть
непустой. Например, два ключа с метками `0` и `1` дают для постоянного
кандидата `p_train=0.5`. Это проверка формата и базовой линии, не рекомендация
использовать две строки для настоящего обучения.

В `candidates.json` должны присутствовать `constant`, `logistic` и `tree`.
Если log loss нескольких кандидатов различается не более чем на `1e-12`,
применяется опубликованный порядок: константа, затем логистическая регрессия,
затем дерево; внутри семейства — лексикографически меньший `experiment_id`.
Test не участвует в этом решении.

## Метрики и группы

Для двух test-примеров `(label, probability) = (1, 0.8), (0, 0.2)` средний
log loss равен `0.2231435513142097` с натуральным логарифмом. Прогнозы
сохраняются как исходные значения из `[0, 1]`; clipping до `[1e-12,1-1e-12]`
применяется только во время вычисления log loss.

Срез `order_count_eq_1` определяется по сохранённому прошлому признаку. При
пустом срезе обе метрики имеют `null`, причины `empty_group`, а `n=0` и
`n_positive=0`. При непустой группе с одним классом log loss остаётся числом,
ROC-AUC имеет `null` и причину `single_class`. Нельзя подменять эти значения
нулём или `0.5`.

## Отказы интерфейса

| Вход | Ожидаемый результат |
| --- | --- |
| Хеш CSV не совпадает с запросом | Стадия `stage_input` завершается отказом с `INPUT_HASH_MISMATCH`. |
| Окно истории или метки выходит за объявленное наблюдение | Отказ с `INCOMPLETE_OBSERVATION`; готовый результат не публикуется. |
| Пустой train | Отказ с `EMPTY_TRAIN`. |
| Train содержит один класс | Отказ с `TRAIN_SINGLE_CLASS`. |
| Пустой validation | Отказ с `EMPTY_VALIDATION`. |

## Повторный запуск

Повтор одинаковой стадии для одного `execution_id` заменяет её логический
результат и удаляет старые part-файлы этого результата. Повтор с новым
`execution_id` оставляет предыдущую успешную историю и обновляет только
`current.json` после публикации нового полного результата. Нельзя очищать
bucket или experiment целиком.

## Граница локальной и серверной проверки

Команда `sh check.sh HW3` запускает публичный toy-сценарий: Compose, DAG,
временные примеры, хеши артефактов, повтор и сохранность хранилищ. Сценарии
выше — примеры входов и наблюдаемых выходов; они не являются реализацией
окон, разметки, обучения или выбора кандидата.

Сервер проверяет тот же опубликованный контракт на дополнительных историях и
запускает проект целиком и сверяет наблюдаемые артефакты с контрактом.
Сервер не вводит новых требований, но локальный PASS не заменяет
серверный результат. Неизменённый starter не проходит полный запуск: это
ожидаемый `FAILED`, пока студент не реализует стадии DAG.
