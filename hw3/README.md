# Домашняя работа 3. Временная модель повторной покупки

В этой работе вы продолжаете тот же репозиторий и проект HW2. Spark строит
временные примеры из истории Online Retail II, Airflow запускает этапы,
SeaweedFS хранит результаты, а MLflow связывает эксперименты и выбранный
комплект модели.

Полное [условие](HW3.md) и [технический контракт](TECHNICAL.md) задают окна,
разметку, схемы, кандидатов, критерий выбора, артефакты и проверки.
Стартер даёт условие, данные и локальную проверку. Окружение
(compose, Dockerfiles, DAG) и код решения вы создаёте сами по контракту.

## Что нужно реализовать

Создайте проект по [техконтракту](TECHNICAL.md): `compose.yaml` со всеми
обязательными сервисами, Dockerfile(ы), DAG `online_retail_training`
с пятью обязательными задачами, код решения (структура каталогов и модулей —
на ваше усмотрение, контракт описывает входы/выходы стадий в разделе 4),
`config/candidates.json` и `requirements.lock`. Самостоятельно реализуйте
построение временных окон и
примеров, разметку, Spark-агрегации, обучение и сравнение кандидатов, заморозку
выбранной модели, оценку и загрузку bundle. В `candidates.json` объявите одну
константу с `experiment_id="constant"`, хотя бы один логистический кандидат и
хотя бы одно дерево по схеме контракта; гиперпараметры выбираете сами.

## Данные

Полный нормализованный gzip не хранится в Git. Курс передаёт защищённую
ссылку или путь к каноническому файлу вместе с выдачей. Получите его до
запуска обработки:

```sh
python3 hw3/data/download.py --source /путь/к/online-retail-ii-v1.csv.gz
# либо переданный курсом URL:
python3 hw3/data/download.py --source "$HW3_CANONICAL_SOURCE"
```

Скрипт проверяет SHA-256 из контракта и сохраняет файл в
`hw3/data/online-retail-ii-v1.csv.gz`. Сам starter не содержит адреса и
учётных данных для защищённого источника. Файл игнорируется Git.

Для локальной разработки в `data/probes/` лежит маленькая независимая история
и запрос. Её ожидаемые свойства описаны в
[data/probes/README.md](data/probes/README.md). Это примеры границ и форматов,
а не алгоритм для полного набора.
Остальные независимые сценарии интерфейса, метрик и повторов собраны в
[data/SCENARIOS.md](data/SCENARIOS.md).

## Запуск среды

Команды ниже работают после того, как вы собрали проект.

Compose должен монтировать `hw3/data/` в `/input` только для чтения и не
публиковать порты на хост. Для отдельного каталога входа используйте
`HW3_INPUT_DIR`; это единственный bind mount, который может быть передан
проверяющим. Команды запуска и локальные учётные данные сервисов определяете
в README своей реализации; они не должны давать доступ к внешней среде.

Ваша реализация запускает DAG `online_retail_training` с
`dag_run_id`, равным `execution_id`, и `conf` вида
`{"request_path":"/input/..."}`. Не скачивайте историю или зависимости из
реализации во время DAG.

## Проверка и сдача

Команда из корня проверяет границы Compose-проекта, запускает DAG на
опубликованном маленьком сценарии и сверяет временные примеры с
`data/expected.json`:

```sh
sh check.sh HW3
```

Локальная проверка также сверяет хеши опубликованных артефактов, повтор одного
исполнения, новое исполнение, отказ до публикации и сохранность результатов
после пересоздания хранилищ. Неизменённый starter ожидаемо завершится
`FAILED`: в нём нет реализации стадий DAG. Это результат неполноты решения,
а не готовое решение или ошибка checker.

Сервер запускает весь проект и наблюдает DAG, S3, MLflow и опубликованные
артефакты на дополнительных историях. Он не добавляет новых требований;
локальный PASS не заменяет серверную проверку. Сдача использует маркер
`MLSD-HW: HW3`. Обычная оценка начинается 2 ноября в 18:00 МСК, мягкий
дедлайн — 9 ноября в 18:00 МСК, жёсткий — 16 ноября в 18:00 МСК.

HW1 и HW2 сохраняются без изменений: `sh check.sh HW1` и `sh check.sh HW2`
работают по прежним контрактам.
