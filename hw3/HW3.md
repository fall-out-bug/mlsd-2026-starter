## Задача

Для клиента Online Retail II на дату `t` оценить вероятность хотя бы одной
положительной покупки в следующие 30 дней. Прогноз нужен клиентам, у которых
есть хотя бы одна положительная покупка в предыдущие 90 дней.
Состав клиентов определяется по прошлому, без использования будущих покупок.

Нужно самостоятельно построить обучающие примеры, сравнить модели, получить
проверяемую оценку и сохранить комплект, пригодный для применения в HW4.
Победа более сложной модели не гарантируется и не заменяет правильного решения.

| Поле | Смысл и представление |

## 2. Объект, окна и признаки

Один пример имеет ключ `(customer_id, as_of)`, где `as_of = t`.
Один клиент может встречаться на нескольких датах: проверяем будущее поведение
в том числе уже известных клиентов. Ключ не входит в признаки модели.

**Положительная покупка** — строка с непустым `customer_id`, `quantity > 0`,
`unit_price > 0` и `invoice_id`, не начинающимся с `C` без учёта регистра.
Пустое описание товара не исключает строку. Одинаковые товарные строки
не удаляются. Одного подходящего товара достаточно для наличия покупки;
число заказов считается по различным `invoice_id`.

| Часть примера | Определение |
| --- | --- |
| История признаков | Положительные покупки в `[t−90 дней, t)` |
| Допустимый клиент | Хотя бы одна такая покупка в истории на эту дату |
| Метка `label = 1` | Есть хотя бы одна положительная покупка в `[t, t+30 дней)` |
| Метка `label = 0` | Таких покупок нет, а весь будущий период полностью наблюдён |
| Неполное наблюдение | Отсутствие покупки нельзя считать нулём; такой снимок непригоден для полностью размеченной выборки |

В полуоткрытом интервале начало входит, конец не входит. Используются
календарные дни и единая шкала времени источника. Ноль означает отсутствие
зарегистрированной положительной покупки за 30 дней, а не окончательный
уход клиента. Последующий возврат не отменяет уже зарегистрированную покупку
и не меняет цель на «покупку за вычетом возвратов».

| Признак | Значение по истории клиента | Тип в таблице примеров |
| --- | --- | --- |
| `order_count` | Число различных `invoice_id` | long |
| `total_amount` | Сумма `quantity × unit_price` | decimal(20,6) |
| `average_order_amount` | `total_amount / order_count` | decimal(20,2) |

Денежные агрегаты вычисляются в decimal, не через float/double.
Цена приводится к `decimal(20,6)`, средний чек округляется half even:
1.005 → 1.00, 1.015 → 1.02. После точного расчёта признаков их числовое
представление для алгоритма обучения может быть вещественным.
Это сохраняет правила [HW2, закреплённая версия стартера](https://github.com/fall-out-bug/mlsd-2026-starter/blob/dd8894bcb808682b3e766513c88e33565d74d3c7/hw2/README.md).

Итого таблица примеров содержит ключ, три признака, `label` и `split`.
Пары ключей уникальны, обязательные поля не содержат пропусков.
Все допустимые клиенты входят в соответствующую часть; отрицательные примеры
не отбрасываются, выборки не балансируются удалением или дублированием строк.
Только три указанных признака используются в обязательном сравнении.
Идентификатор, дата, метка, страна, будущие события и дополнительные признаки
не подаются в модель.

## 4. Кандидаты и выбор

Обязательны три кандидата:

1. Постоянная вероятность `p_train`: доля единиц среди всех примеров train.
2. Логистическая регрессия, обученная на train.
3. Одно дерево классификации, обученное на train с ограничениями ниже.

| Настройка дерева | Допустимое значение |
| --- | --- |
| Максимальная глубина `max_depth` | Одно из `2, 3, 4, 5` |
| Минимум обучающих примеров в листе `min_samples_leaf` | Одно из `20, 50, 100` (целое число примеров) |
| Критерий разбиения `criterion` | `gini` |
| Выбор разбиения `splitter` | `best` |
| Веса классов `class_weight` | `None` |
| Случайное состояние `random_state` | `2026` |

Хотя бы одна допустимая пара глубины и размера листа обязательна;
перебирать все 12 сочетаний не требуется. Значения выбираются и обосновываются
до финальной оценки. Другие настройки дерева сохраняются стандартными
для закреплённой версии библиотеки и записываются в эксперимент.
Ансамбль не заменяет обязательное одиночное дерево.
Смысл настроек описан в [документации DecisionTreeClassifier](https://scikit-learn.org/stable/modules/generated/sklearn.tree.DecisionTreeClassifier.html).

Настройки логистической регрессии и необходимость масштабирования студент
выбирает самостоятельно и указывает в отчёте. Зависимые от данных параметры
обработки оцениваются только на train. В обязательном сравнении каждый пример
имеет одинаковый вес; веса классов и примеров не меняются. Случайное состояние
у алгоритмов, где оно используется, фиксируется как `2026`.

**Критерий выбора — минимальный log loss на всём validation.** Все варианты
оцениваются на одинаковых ключах. Допускается несколько настроек обучаемых
моделей; все запуски, участвовавшие в выборе, сохраняются. Полный поиск
гиперпараметров не обязателен.

Значения в пределах `1e-12` от минимального validation log loss считаются
равными для выбора. Среди них предпочитается константа, затем логистическая
регрессия, затем дерево. При равенстве внутри одного семейства выбирается
вариант с лексикографически меньшим `experiment_id`. Это заданное студентом
стабильное строковое имя конфигурации, уникальное среди сравниваемых вариантов
и сохраняемое при повторных запусках; оно назначается до test и не является
случайным `run_id` MLflow. Это техническое правило повторяемости, не доказательство
статистического превосходства.

Обе обучаемые модели обязательны даже при победе константы.
**После выбора переобучения на train + validation нет.** Фиксируются
обработка, модель и выбранный запуск, затем оценивается test. Test не
используется для выбора, настройки или замены среза. Открытость исходной
истории не делает test скрытым; протокол работы студент соблюдает и описывает.

## 5. Общая оценка и обязательный срез

После выбора рассчитайте метрики выбранного варианта и константы `p_train`
на **одних и тех же test-примерах**, в целом и на срезе:

> `order_count = 1` за 90 дней перед датой снимка.

Это клиенты с одним различным положительным заказом в текущей истории,
а не обязательно новые клиенты магазина. Срез определяется только по
прошлым признакам и не зависит от метки или прогнозов. Его смысл — проверить,
как ведёт себя модель при небольшом количестве недавних взаимодействий.
По результату test правило группы и модель уже не меняются.

Для каждой оценённой группы укажите число примеров `n`, число единиц `n_positive`,
log loss и ROC-AUC. Основная метрика — средний по примерам бинарный log loss
с натуральным логарифмом. Для его расчёта используется
`p_clipped = min(max(p, 1e-12), 1 - 1e-12)`; эта политика одинакова для всех
кандидатов. Исходные вероятности конечны и принадлежат `[0,1]`, сохраняются
без округления для показа; clipping не меняет сохранённый прогноз.
ROC-AUC вычисляется по исходным вероятностям, равные значения имеют половинный
вклад при сравнении положительного и отрицательного примера.

Для одного класса ROC-AUC отсутствует с объяснением причины. Для пустой
группы отсутствуют обе метрики. Их нельзя заменять нулём или 0,5.
Для независимого пересчёта метрик и совпадения вероятностей после загрузки
задаётся абсолютный допуск `1e-9`, без относительного допуска.

В отчёте сравните результат с константой и объясните различие общей оценки
и среза. Порог обязательного превосходства не задаётся; корректный вывод
о слабой модели допустим. Эти четыре оценки на test — выбранный вариант
и константа, каждый в целом и на срезе — обязательны даже при выборе константы.

Для константы комплект сохраняет `p_train`, ожидаемую схему входа и версию;

Pipeline с обработкой, схема, lock зависимостей и манифест идентичности;
для константы используется DummyClassifier с постоянной вероятностью train.
Сведения сохраняются для всех сравниваемых запусков, а полный комплект для
применения и проверка его загрузки обязательны для выбранного варианта.

Признаки HW3 хранятся отдельно от выходов HW2, с ключом клиент/дата.
Прежние четыре столбца, одна строка на клиента, пути и режим HW2 сохраняются.
Переиспользуется собственный расчёт, а не готовые значения из Redis HW2.
Организация кода остаётся самостоятельным решением.

## 7. Сдача через Git и самостоятельность

Коммит фиксирует реализацию, из которой воспроизводится результат.
Скриншот MLflow или переписанная таблица метрик не заменяют вычисления.
[Технический контракт](TECHNICAL.md) задаёт состав Git-сдачи, команды,
форматы/пути, закрепление зависимостей, хранение артефактов, ресурсы и классы
проверок. Локальная и серверная проверка наблюдают только требования этого
документа и технического контракта. Новые содержательные требования после
выдачи, на L06 или только в закрытом checker не добавляются.

| Свойство | Что должен наблюдать автоматический проверяющий |
| --- | --- |
| Временные примеры | На контрольной истории выполнены отбор клиентов, границы окон, правила покупки, точные агрегаты, полнота и метки |
| Отрицательные примеры | Допустимый клиент без будущей покупки остаётся с 0 при полном наблюдении |
| Допустимость информации | Изменение будущего не меняет прошлые признаки и состав клиентов; обучаемая обработка определяется только train |
| Обучение и сравнение | Обе модели обучены; ограничения дерева и правило выбора соблюдены; настройки и результаты связаны с запусками |
| Метрики | Пересчёт по сопоставленным ключам и исходным прогнозам совпадает с отчётом в допуске |
| Комплект | После загрузки в новом процессе воспроизводятся вероятности выбранной версии |
| Повторяемость | Повторный запуск не накапливает дубли, сохранённые выходы относятся к текущему запуску |

Это требования к наблюдаемому результату, а не утверждение о готовом checker.
Артефакты сами по себе не доказывают, что студент не смотрел в test при выборе.
Закрытыми могут быть контрольные данные, но не новые требования.

После L05 студент сам соединяет понятия в реализацию. Готового алгоритма
