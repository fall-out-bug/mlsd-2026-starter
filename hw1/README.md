# Домашняя работа 1: воспроизводимый запуск сервиса в Docker

## Цель задания

Собрать сервис в Docker. Он должен отвечать на `GET /health` за две секунды JSON-объектом с полем `"status":"ok"`. Другие поля допустимы. Язык и фреймворк выбираете вы.

## Окружение

Работайте в своём репозитории, созданном из шаблона курса, в ветке `main`. Файлы решения лежат в корне; в `hw1/` находится условие задания. Все команды ниже выполняются из корня.

Нужны Git, Docker Desktop или Docker Engine с работающим Docker daemon и команды WSL/Linux: `sh`, `curl`, `awk`, `grep`, `date`, `rm`, `timeout`. Проверьте Docker:

```sh
docker version
```

В выводе должны быть разделы Client и Server.

Если предпочтений нет, используйте Python 3.12, образ `python:3.12-slim`, `requirements.lock` и Docker Engine или Docker Desktop 24+ под WSL2/Linux.

## Задача

Добавьте в корень репозитория:

- `Dockerfile`;
- один файл закреплённых зависимостей;
- код сервиса;
- `README.md` с командами сборки и запуска.

### Dockerfile

Каждая строка `FROM`, кроме `FROM scratch`, и каждый `COPY --from=<образ>` должны закреплять образ дайджестом: `image@sha256:<64 символа>`. Финальная стадия должна использовать базовый образ с Python. Сборка из нескольких стадий допускается, если все образы закреплены дайджестами.

Для уже скачанного образа дайджест можно получить командой:

```sh
docker inspect --format '{{index .RepoDigests 0}}' python:3.12-slim
```

Полученную строку целиком используйте в `FROM`. Не добавляйте `# syntax=...`: сервер использует встроенный frontend сборки.

### Зависимости

Допустимые файлы: `uv.lock`, `poetry.lock`, `Pipfile.lock`, `requirements.lock`, `package-lock.json`, `npm-shrinkwrap.json`, `pnpm-lock.yaml`, `yarn.lock`, `Cargo.lock`, `go.sum`. Если зависимостей нет, файл всё равно нужен; например, минимальный `uv.lock` с одной строкой `version = 1`.

Сервер собирает образ без сети. Зависимости из `requirements.lock` и `uv.lock` сервер устанавливает сам. Для `uv.lock` добавьте в Dockerfile `COPY --from=ghcr.io/astral-sh/uv@sha256:<дайджест> /uv /usr/local/bin/uv`: сервер заранее кеширует пакеты из lock-файла. При других файлах зависимостей сервис должен собираться без внешних пакетов.

### README и запуск

В README укажите обычные команды сборки и запуска. Контекст сборки — `.`, порт запуска — `8080`. Например:

```sh
docker build --tag hw1 .
docker run --publish 8080:8080 hw1
```

`Dockerfile` и эти две команды обязательны. Docker Compose можно добавить для удобства.

## Локальная проверка

Из корня репозитория выполните:

```sh
sh check.sh HW1
```

Скрипт проверит файлы, соберёт образ, запустит контейнер, обратится к `/health` и удалит созданные контейнер и образ.

При `FAIL` исправьте указанную проблему и повторите `sh check.sh HW1`. После исправления отправьте новый коммит с маркером `MLSD-HW: HW1`. Локальный `PASS` означает успешную проверку на вашей машине; оценку выставляет сервер курса.

## Бонус +2: OpenSpec

OpenSpec-пакет — необязательная работа для бонуса +2. Его можно отправить сразу или отдельно от кода.

Чекер ищет пакет в `openspec/changes/` от корня репозитория.

В `openspec/changes/<имя-изменения>/`, например `hw1-health-service`, подготовьте:

- `proposal.md` — зачем изменение, что меняется и что не входит в него;
- `tasks.md` — список задач;
- `specs/<capability>/spec.md` — требования и сценарии «WHEN … THEN …».

Для отправки используйте маркер `MLSD-HW: HW1`. Проверка пакета начинается после зачёта кода; повторно отправлять зачтённый код не нужно. Опишите ожидаемое поведение решения так, чтобы его понял человек, не видевший ваш код. Результат придёт в Telegram и появится на коммите в GitHub.
